1. Tło

Dla początkujących: czym jest monomorfizacja (można pominąć)

Funkcja generyczna id<T>(x: T): T jest przepisem, a nie gotową funkcją: procesor nie wie, ile bajtów ma T. Monomorfizacja (mono) zamienia przepis na gotowe wersje: dla każdego typu, z którym funkcję faktycznie wywołano, powstaje osobna kopia z podstawionym typem, np. id<i32> i id<String>. Ten sam pomysł stosuje Rust i C++.

Zaletą jest szybki kod (brak dynamicznego rozstrzygania typów), a ceną większy program i konieczność ustalenia, które kopie są potrzebne.

Stan przed zmianą

Po #44–#46 kompilator umie sprawdzić typy i własność generycznego kodu, ale nie umie go wykonać. codegen_gate odrzuca każdą funkcję i klasę generyczną, bo cały potok (frontend.rs) pracuje na jednym HIR, w którym wciąż siedzą parametry typu (TyData::Param). Ticket #47 dodaje brakujący etap: z generycznego HIR robi konkretny, bez żadnego Param. Generowanie LLVM z tego wyniku to osobny ticket (TS-P3-07).

2. Intuicja

Idea: lista robocza od main

Nie chcemy kopii wszystkiego, tylko tego, co program rzeczywiście używa. Zaczynamy od main. Przeglądamy jego ciało; za każdym razem, gdy trafiamy na wywołanie funkcji, ustalamy z jakimi argumentami typu je wywołano i dopisujemy taką instancję do kolejki. Potem bierzemy z kolejki następną instancję i robimy to samo, aż kolejka się opróżni.

3. Instancje

id<i32>id<String>(id(2) to ta sama co id(1))

Instancja jest identyfikowana przez parę (funkcja, lista argumentów typu). Ponieważ typy są internowane (równy kształt oznacza ten sam TyId), dwa wywołania z i32 trafiają na tę samą instancję bez żadnego dodatkowego porównywania.

Kluczowy problem: skąd wiemy, że T = i32?

Typeck w trakcie sprawdzania wywołania id(1) wyliczył, że T = i32, ale tę informację wyrzucił: HIR jej nie przechowuje. Zostało jednak coś równie dobrego: typ samego callee. Wywołanie id(1) ma w HIR callee o typie (i32) -> i32, czyli sygnaturę po podstawieniu. Mamy też oryginalną sygnaturę (T) -> T. Wystarczy je dopasować.

Sygnatura generycznaTyp callee w wywołaniuWynik dopasowania
(T) -> T(i32) -> i32T = i32
(A, B) -> A(i32, String) -> i32A = i32, B = String
(&Pair<A, B>) -> A (metoda)(&Pair<bool, bool>) -> boolA = bool, B = bool
(T) -> T(i32) -> Stringkonflikt: T ma dwa typy
Luka tej metody Jeśli parametr typu nie występuje w żadnym parametrze ani w typie zwracanym (fun f<T>(): i32, wywołane jako f::<i32>()), to nic nie da się dopasować. Takie przypadki zgłaszamy jako błąd ("not determined by its signature"), zamiast zgadywać.

Co robi instancja z ciałem funkcji

Instancja to klon generycznej funkcji, w którym każdy typ przeszedł przez subst (zamiana Param(i) na args[i]), a nazwy wywoływanych funkcji zamieniono na nazwy instancji. Z twice<T>, które woła id(id(x)), powstaje twice<i32> wołające id<i32>. Metody i klasy działają tak samo: p.first() na Pair<i32, String> daje Pair.first<i32,String>, a sama klasa wchodzi do wyniku jako Pair<i32,String> z podstawionymi polami.

Rekurencja polimorficzna

Co, jeśli funkcja woła samą siebie z coraz większym typem?

fun f<T>(var x: T) {
    f(Box(move x))     // f<i32> woła f<Box<i32>> woła f<Box<Box<i32>>> ...
}

Instancji byłoby nieskończenie wiele, więc lista robocza nigdy by się nie skończyła. Rozwiązanie jest proste: gdy argument typu jest zagnieżdżony głębiej niż 32 poziomy, kończymy z diagnostyką "polymorphic recursion". To jedyny błąd dla użytkownika, jaki może powstać już po mono.

Pułapka wydajności: typy to grafy, nie drzewa Typ Pair<T, T> ma dwa razy to samo dziecko. Przy rekurencji, która podwaja typ w każdym kroku, naiwne liczenie głębokości odwiedzałoby 232 węzły, zanim doszłoby do limitu. Dlatego depth pamięta wyniki dla już policzonych TyId (memoizacja).

Po sklonowaniu: raporty i numery węzłów

Dalsze etapy (escape, plan pamięci, region_walk) wymagają, żeby raport z analizy własności miał dokładnie jeden korzeń na funkcję, w tej samej kolejności. Dlatego dla każdej instancji klonujemy korzeń jej generycznego oryginału i zmieniamy etykietę na nazwę instancji. Skopiowane ciała mają te same NodeId, więc po złożeniu całego programu numerujemy je od nowa (number_nodes); dzięki temu id są unikalne w całym wyniku. Dopiero wtedy uruchamiamy escape i plan pamięci, już na konkretnych typach.

Czego ten PR nie robi Nie podłącza mono do frontend::check ani do bork build; generyki są nadal odrzucane przez bramkę, dopóki TS-P3-07 nie wygeneruje z wyniku kodu. Wynik zawiera tylko to, co osiągalne z main, więc nieużywane funkcje niegeneryczne są w nim pominięte.

3. Kod krok po kroku

3.1 Walker z callbackiem (src/hir/resolve.rs)

Istniejący walker przepisywał typy w ciele funkcji (do podmiany zmiennych inferencji). Dostał drugi callback wywoływany po przetworzeniu dzieci każdego wyrażenia, więc w chwili odwiedzenia wywołania typ callee jest już ostateczny.

+ pub fn rewrite(body, f: &mut impl FnMut(TyId) -> TyId, on_expr: &mut impl FnMut(&mut HirExpr)) {
+     block(body, f, on_expr);
+ }
  pub fn resolve_types(body, f) {
-     block(body, f);
+     rewrite(body, f, &mut |_| {});
  }

3.2 Dopasowanie typów (bind)

fn bind(tcx, pattern: TyId, actual: TyId, out: &mut [Option<TyId>]) -> bool {
    if !tcx.has_param(pattern) { return pattern == actual; }    // brak parametrów: muszą być równe
    match (tcx.data(pattern), tcx.data(actual)) {
        (Param(idx), _) => /* zapisz out[idx] = actual, albo sprawdź zgodność z poprzednim */,
        (Class(d1, a1), Class(d2, a2)) => d1 == d2 && wszystkie argumenty pasują,
        /* Array, Func, Ref, ManagedRef, Vec, Range, Nullable: schodzimy w dzieci */
        _ => false,
    }
}

Jeśli ten sam parametr trafi na dwa różne typy, dopasowanie się nie udaje. Zwracana wartość Vec<Option<TyId>> mówi też, które parametry zostały nieustalone (luka opisana wyżej).

3.3 Kolektor (Collector)

  • intern: sprawdza głębokość argumentów, szuka klucza (indeks funkcji, argumenty) w mapie, a przy pierwszym spotkaniu tworzy Instance, nadaje nazwę (id<i32>) i dokłada do kolejki.
  • call_args: dla niegenerycznego callee zwraca pustą listę; dla generycznego dopasowuje parametry i typ zwracany do typu callee i zgłasza błąd, gdy coś zostanie nieustalone.
  • visit: dla wywołania, którego callee jest identyfikatorem funkcji użytkownika, podmienia nazwę na nazwę instancji. Dla ObjectConstruct i ObjectField podmienia nazwę klasy na nazwę jej instancji.

Nazwy to wydruk typu bez spacji (Pair.first<i32,String>). Znak < nie może wystąpić w identyfikatorze użytkownika, więc nazwa instancji nie zderzy się z żadną zwykłą funkcją.

3.4 Pętla główna (monomorphize)

  1. Sprawdza, że raport ma tyle korzeni co funkcji (inaczej błąd zamiast paniki).
  2. Zasiewa kolejkę funkcją main.
  3. Dla każdej instancji: klonuje oryginał, podstawia argumenty w parametrach, typie zwracanym i ciele (resolve_types z subst; nieudane podstawienie T?? to diagnostyka), potem rewrite z visit przepisuje wywołania.
  4. Zbiera instancje klas z typów funkcji oraz z pól klas niegenerycznych i dla każdej buduje HirClass z podstawionymi polami. Zbiór seen chroni przed powtórzeniami, a limit głębokości przed nieskończonym rozrostem.
  5. Składa raport (sklonowane i przemianowane korzenie), numeruje węzły, uruchamia escape, memory::plan i stamp_codegen_push.

W kompilacji debug debug_assert!(no_params_left(..)) sprawdza, że żaden typ w wyniku nie zawiera Param.

3.5 Testy i snapshot

  • src/mono/tests.rs (11 testów): dwie różne instancje id, brak instancji dla nieużywanych generyków, twice woła id, wzajemna rekurencja ping/pong kończy się, metody i klasy na dwóch zestawach argumentów, unikalność NodeId, odrzucenie rekurencji polimorficznej i parametru spoza sygnatury, brak Param w wyniku, klasa w polu klasy zwykłej.
  • tests/mono_instances_golden.rs + tests/golden/mono_instances.txt: lista instancji i klas dla 7 programów generycznych z korpusu. Odświeżanie: BORK_BLESS=1.

4. Quiz

Pięć pytań. Kliknij odpowiedź, a dostaniesz informację zwrotną.

1. HIR nie zapamiętuje argumentów typu wywołań. Jak mono ustala, że w id(1) parametr T to i32?

Typ callee w HIR jest sygnaturą po podstawieniu, więc jednostronne dopasowanie wzorca (bind) odtwarza argumenty. Żadnej dodatkowej tabeli nie ma, a typeck nie jest uruchamiany ponownie.

2. Dla jakiego programu dopasowanie argumentów nie zadziała i mono zgłosi błąd?

Dwa różne typy dają po prostu dwie instancje, a wołanie innych generyków i klasy w argumentach działają (są w testach). Bez wystąpienia w sygnaturze nie ma czego dopasować.

3. Dlaczego rekurencja polimorficzna jest wykrywana limitem głębokości typu, a nie np. limitem liczby instancji?

Zwykła rekurencja, np. f<i32> wołające f<i32>, ma tę samą instancję i się nie rozrasta. Dopiero ciągłe powiększanie typu daje nieskończenie wiele instancji, a głębokość to właśnie wykrywa.

4. Po co depth pamięta wyniki dla już policzonych typów?

Przy rekurencji, która podwaja typ, naiwne liczenie odwiedzałoby rzędu 2n węzłów, zanim dojdzie do limitu 32. Memoizacja po TyId sprowadza to do liczby różnych typów.

5. Dlaczego dla każdej instancji trzeba sklonować i przemianować korzeń raportu z analizy własności, a po złożeniu programu wywołać number_nodes?

Raport powstał z AST przed mono, więc ma korzeń na funkcję generyczną. check_roots porównuje liczbę i etykiety, więc bez przemianowania plan pamięci zakończyłby się błędem. LLVM nie jest tu jeszcze używany (to TS-P3-07).
