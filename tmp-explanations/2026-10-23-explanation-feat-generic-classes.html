1. Tło

Dla początkujących: klasa generyczna i rozmiar obiektu (można pominąć)

Klasa generyczna to klasa z parametrem typu, który wypełnia się przy użyciu:

class Pair<A, B> {
    a: A
    b: B
}

Pair<i32, String> to para liczby i napisu, a Pair<bool, bool> to para wartości logicznych. Są to różne typy zbudowane z jednej definicji.

W językach, które trzymają obiekty „w środku" innych obiektów (by-value), pojawia się problem rozmiaru. Klasa class Bad { b: Bad } zawierałaby samą siebie, która zawierałaby samą siebie, i tak w nieskończoność, więc nie ma skończonego rozmiaru. Rozwiązaniem jest pośrednictwo: pole typu Ref<Bad> trzyma tylko uchwyt o stałym rozmiarze, więc rekurencja przez Ref jest dozwolona. Tak powstają listy i drzewa.

Stan przed zmianą

Poprzednie PR-y zbudowały większość fundamentów generyków. Parser rozumie class Box<T> (#42). Deklaracje są walidowane (#43). Funkcje generyczne są sprawdzane z nieprzezroczystym T i wywoływane przez wnioskowanie typów (#44, zmergowane jako 6f185f6). Klasy były jednak dalej „declaration-only": definicja class Pair<A,B> przechodziła, ale każde jej użycie dawało błąd.

Powód był prosty. Typ klasy w TyData to było Class(DefId), czyli tylko tożsamość definicji. Nie było gdzie zapisać, że chodzi o Pair<i32, String>, a nie o Pair<bool, bool>. Walidator layoutu (validate_owned_layouts) umiał wykryć cykl tylko między niegenerycznymi klasami, bo śledził same DefId.

2. Intuicja

Cała zmiana wynika z jednego ruchu: typ klasy dostaje argumenty. Reszta to konsekwencje, które trzeba pokazać w czterech miejscach.

Ruch pierwszy: Class(DefId) staje się Class(DefId, Vec<TyId>)

Zapis w kodziePrzedPo
Point (zwykła klasa)Class(Point)Class(Point, [])
Pair<i32, String>(nie do wyrażenia)Class(Pair, [i32, String])
Pair<bool, bool>(nie do wyrażenia)Class(Pair, [bool, bool]) inny typ

Typy są internowane: każdy kształt dostaje jeden identyfikator TyId, więc porównanie typów to porównanie liczb. Dodanie argumentów do kształtu automatycznie rozróżnia Pair<i32,String> od Pair<bool,bool>, bez żadnego dodatkowego kodu porównującego.

Ruch drugi: pola i metody są napisane na Param, a podstawiane przy użyciu

Definicja klasy mówi, że pole a ma typ A, czyli Param(0). Dopiero gdy mamy konkretnego odbiorcę typu Pair<i32, String>, podstawiamy za Param(0) typ i32 i dostajemy typ pola i32.

Definicja

class Pair<A, B>a: Param(0)b: Param(1)
+

Odbiorca

p: Pair<i32, String>args = [i32, String]
→

Wynik

p.a : i32p.b : String

Ten sam mechanizm (subst, który istniał od #34) działa dla pól, przypisań do pól i sygnatur metod. Nowy jest tylko jeden wspólny helper, Env::member_ty.

Ruch trzeci: konstruktor wnioskuje argumenty

Wywołanie Pair(1, "a") nie podaje A ani B. Checker postępuje tak samo jak przy funkcjach generycznych w #44: tworzy świeże zmienne inferencji, wstawia je za parametry i pozwala argumentom je ustalić.

1. Świeże zmienne

Pair<?0, ?1>pola: a: ?0, b: ?1
→

2. Argumenty

1 ~ ?0 (Int)"a" ~ ?1 (String)
→

3. Domyślne literały

?0 := i32
→

Wynik

Pair<i32, String>

Typ oczekiwany też pomaga. W val q: Pair<i64, String> = Pair(1, "b") checker najpierw unifikuje Pair<?0,?1> z Pair<i64,String>, więc literał 1 od razu jest i64. To wymagało nowej reguły w unifikacji: dwa typy klas unifikują się, gdy mają ten sam DefId i ich argumenty unifikują się parami.

Ruch czwarty: walidator layoutu patrzy na instancje, nie na definicje

Samo śledzenie DefId nie wystarcza. Weźmy:

class Box<T> { v: T }
class A { b: Box<A> }

Żadna z tych klas osobno nie zawiera siebie. Razem tak: A zawiera Box<A>, a ten zawiera pole v typu T = A. Cykl jest widoczny dopiero po podstawieniu. Dlatego walidator przechodzi po instancjach:

A

b: Box<A>
→

Box<A>

v: TT := A, więc v: A
→

wracamy do A

A -> Box<A> -> A
Dlaczego Ref jest wyjątkiem Walidator nie wchodzi w typ ManagedRef. Pole next: Ref<Node<T>> nigdy nie jest ścieżką „przez wartość", więc class Node<T> { v: T; next: Ref<Node<T>> } jest poprawna. Ta zasada nie wymagała zmiany, bo opiera się na tym, że held zwraca tylko Class i tablice klas.
Pułapka: typy, które się rozrastają class N<T> { x: N<N<T>> } nie powtarza żadnego typu: N<T>, potem N<N<T>>, potem N<N<N<T>>>… Zbiór „już odwiedzone" nigdy się nie zatrzyma, więc walidator ma limit głębokości 32 i po jego przekroczeniu uznaje klasę za cykliczną.

Czego ten PR nie robi

  • Nie generuje kodu. codegen_gate odrzuca klasy generyczne tak samo jak funkcje: „not compiled yet (monomorphization)".
  • Nie ma jawnych argumentów przy konstruktorze. Pair::<i32,String>(..) daje czytelny błąd, a typ ustala się adnotacją przy wiązaniu.
  • Nie ma ograniczeń (bounds). Operatory i porównania na T nadal są zabronione, jak w #44.

3. Kod krok po kroku

3.1 Typ z argumentami (src/ty/*)

  • ty/mod.rs: wariant Class(DefId, Vec<TyId>).
  • ty/query.rs: TyCtx::class(def, args) oraz nowe class_args(ty), które zwraca klasę i jej argumenty przez Ref, ManagedRef i ?. Zapytania zwracające samo DefId (record_def, class_def) zostały bez zmian.
  • ty/fold.rs: argumenty trafiają do children() i dostają własną gałąź w super_fold (wcześniej Class był liściem). Przez to subst, rozwiązywanie zmiennych i has_infer widzą argumenty bez dodatkowego kodu.
  • ty/print.rs: drukuje Pair<i32, String>, tak jak Vec<..>.
  • infer/unify.rs: nowa reguła dla dwóch klas.
+ (TyData::Class(da, xa), TyData::Class(db, xb)) => {
+     if da != db || xa.len() != xb.len() {
+         return Err(mismatch);
+     }
+     for (x, y) in xa.into_iter().zip(xb) {
+         self.unify_inner(tcx, x, y)?;
+     }
+     Ok(())
+ }
Dlaczego fold.rs jest krytyczny Gdyby Class został liściem w super_fold, zmienne inferencji ukryte w Pair<?0, ?1> nigdy by się nie rozwiązały i trafiłyby do HIR, a to jest naruszenie niezmiennika „żadna zmienna inferencji nie dociera do HIR" z #41.

3.2 Lowering i deklaracje (lower.rs, generics.rs, mod.rs)

  • lower.rs: lower_named teraz zamienia argumenty typu na TyId i przekazuje je do lower_class. Błąd „instantiating generic types is not supported yet (#44)" zniknął. Sprawdzanie arności zostało.
  • generics.rs: usunięto diagnostykę „generic class is declaration-only" oraz całą funkcję declaration_only (ok. 40 linii), bo nikt jej już nie woła.
  • mod.rs / collect_method_sigs: parametr this metody ma teraz typ &Pair<Param(0), Param(1)>, czyli klasę z identycznościowymi argumentami.
  • mod.rs / check_function: wczesny powrót dla metod generycznych zniknął. Zakres parametrów w ciele metody to teraz klasa ++ metoda, w tej kolejności, zgodnie z numeracją w sygnaturze. Wcześniej brano tylko własne parametry funkcji.

3.3 Konstruktor (expr/object.rs, expr/call.rs)

+ let type_args = fresh_params(&class.generics, &class.name, span, env);
+ let ty = env.tcx.class(class.id, type_args.clone());
+ if let Some(expected) = expected { env.same(ty, expected); }   // tylko podpowiedź
  ...
+ let field_ty = subst(env.tcx, field.ty, &type_args)...;
  let value = check(arg, field.ty field_ty, return_ty, env);

fresh_params to wyciągnięta z instantiate (z #44) pętla tworząca zmienną General i wpis PendingParam. Dzięki temu konstruktor, funkcja i metoda używają jednego kodu, a niewywnioskowany parametr zgłasza ten sam błąd „cannot infer type parameter".

Podpowiedź w tym błędzie zależy od callee. Dla funkcji brzmi „specify it explicitly, e.g. f::<..>(..)", a dla konstruktora i metody „annotate the binding with its type to fix it", bo tam turbofisha nie ma. check_call dodatkowo zgłasza osobny komunikat, gdy ktoś poda jawne argumenty konstruktora generycznej klasy.

3.4 Pola i metody (field.rs, assign.rs, method.rs, env.rs)

  • Env::member_ty(receiver, member) pobiera argumenty klasy odbiorcy i robi subst. Używają go odczyt pola, przypisanie do pola i (pośrednio) metody.
  • method.rs: zamiast błędu „calling the generic method … is not supported yet" budowana jest lista argumenty_klasy ++ świeże_zmienne_metody. Argumenty klasy pochodzą z odbiorcy, a świeże zmienne tylko dla własnych parametrów metody (sig.generic_names[class_arity..]). Dzięki temu p.with(true) daje bool.

3.5 Walidacja layoutu (mod.rs)

// dla każdej klasy: origin = Class(def, [Param(0..n)])  — definicja z parametrami jako liśćmi
fn find_cycle(origin, current, classes, tcx, done, path) -> bool {
    if path.len() > MAX_DEPTH { return true; }
    if !done.insert(current) { return false; }          // klucz: TyId instancji, nie DefId
    let Class(def, args) = tcx.data(current).clone() else { return false };
    for field in &classes[&def].fields {
        let field_ty = subst(tcx, field.ty, &args)?;     // podstaw argumenty instancji
        let Some(target) = held(field_ty, tcx) else { continue };
        path.push(target);
        if target == origin || find_cycle(origin, target, ...) { return true; }
        path.pop();
    }
    false
}

Trzy różnice względem starej wersji: zbiór done jest kluczowany przez TyId (instancję), pola są podstawiane przed zejściem głębiej, a ścieżka jest zapamiętywana. Komunikat ma postać class `Bad<T>` has a recursive by-value layout (Bad<T> -> Bad<T>); use `Ref<..>` for the recursive field. Na czas formatowania komunikatu nazwy parametrów są ustawiane przez set_param_names, żeby widać było T, a nie T0.

Klasy są sprawdzane w kolejności alfabetycznej po nazwie, żeby wynik (i pliki złote) był deterministyczny. Cykl wzajemny A ↔ B jest nadal zgłaszany dla obu klas, każda ze swoją ścieżką.

3.6 Brama kodegenu (codegen_gate.rs)

Pętla po hir.classes z niepustymi generics zgłasza „generic class `X` is not compiled yet (monomorphization)". Bez niej klasa generyczna dotarłaby do LLVM, który nie zna Param.

3.7 Testy i dokumentacja

  • src/typeck/tests/generics.rs: trzy testy „declaration-only" przepisano, dodano m.in. wnioskowanie konstruktora, typ oczekiwany, podstawianie pól i metod, niedopasowane argumenty, Ref<Node<T>>, ścieżkę cyklu (też wzajemnego i przez instancję), rozrastającą się rekurencję i bramę kodegenu.
  • programs/check/generics/: generic_class.bork, node_ref.bork. programs/check_fail/generics/: generic_cycle, generic_mutual_cycle, instantiation_cycle, constructor_cannot_infer.
  • Pliki złote (tests/golden/*) przegenerowano. Zmieniły się też stare fixtury, bo komunikat o cyklu ma teraz ścieżkę, a „declaration-only" zniknęło.
  • docs/language.md i RFC 0001 opisują nowe zachowanie.

4. Quiz

Pięć pytań. Kliknij odpowiedź, a dostaniesz informację zwrotną.

1. Dlaczego do TyData::Class dodano listę argumentów, zamiast trzymać argumenty obok, np. w osobnej tabeli?

Gdyby argumenty były poza typem, dwa różne typy miałyby ten sam TyId i trzeba by wszędzie porównywać dodatkową strukturę. Drukowanie nie było problemem (nazwy klas są w osobnej mapie), a parser nie ma tu nic do rzeczy.

2. W super_fold zabrakło przypadkiem gałęzi dla Class(def, args), więc klasa została „liściem". Co by się stało dla val p = Pair(1, "a")?

super_fold jest podstawą m.in. subst i rozwiązywania zmiennych. Bez zejścia do argumentów zmienne zostają niezastąpione. Dlatego plan wymieniał ten plik jako krytyczny.

3. Dlaczego class A { b: Box<A> } z class Box<T> { v: T } jest odrzucane, skoro żadna z klas osobno nie zawiera siebie?

Stary walidator śledził same DefId-y i takiego cyklu by nie zauważył. Nowy chodzi po instancjach i robi subst na polach przed zejściem głębiej.

4. Po co walidator ma limit głębokości (32), skoro zbiór odwiedzonych typów done już chroni przed pętlą?

done łapie cykle, które wracają do tego samego typu. Rozrastające się instancje nigdy do niego nie wracają, więc potrzebny jest limit. Po jego przekroczeniu klasa jest uznana za cykliczną. Ref jest pomijany celowo.

5. Metoda fun with<C>(c: C): C w class Pair<A, B> jest wołana jako p.with(true), gdzie p: Pair<i32, String>. Skąd checker bierze wartości parametrów A, B i C?

Sygnatura metody ma parametry „klasa najpierw, potem metoda". Odbiorca wypełnia prefiks (class_args), a dla reszty (sig.generic_names[class_arity..]) powstają świeże zmienne. Zmienna General nie ma typu domyślnego, a argument true ustala C = bool.
