1. Tło

Dla początkujących: własność, przeniesienie i areny (można pominąć)

W Bork wartość nie-skalarna (np. String albo obiekt klasy) ma jednego właściciela. Zapis val y = move x przenosi wartość z x do y, a po przeniesieniu x nie wolno już użyć. To właśnie błąd „użycia po przeniesieniu". Liczby (i32) są kopiowane, więc tej reguły nie dotyczą.

Bajty napisów i obiektów żyją w arenach: blokach pamięci związanych z zasięgiem (regionem). Gdy region się kończy, jego arena jest zwalniana. Stąd drugi rodzaj błędu: wartość, której bajty leżą w wewnętrznym regionie, nie może „uciec" na zewnątrz (zostać zwrócona ani przypisana do zmiennej z zewnątrz), bo jej pamięć zniknie. Za tę kontrolę odpowiada moduł escape.

Monomorfizacja (mono) to zamiana funkcji generycznej na zwykłe wersje dla konkretnych typów: z id<T> powstają id<String>, id<i32> itd. W Bork jej jeszcze nie ma, więc generyczny kod jest tylko sprawdzany, a nie kompilowany.

Stan przed zmianą

Po #44 i #45 funkcje, klasy i metody generyczne są sprawdzane pod względem typów z nieprzezroczystym parametrem T (TyData::Param), ale codegen_gate nie wpuszcza ich do generowania kodu. Moduły własności (sema, escape, memory) nie pomijają ciał generycznych, więc już teraz się na nich uruchamiają. Pytanie z ticketu #46 brzmi: czy to, co one robią z T, jest bezpieczne?

Kontrakt jest zapisany w RFC 0002 (sekcja 4): nieprzezroczyste T jest move-only (nigdy Copy), a ciało zaakceptowane przed mono nie może stać się niepoprawne dla żadnej instancji (INV-10). Fakty wymagające konkretnego typu (układ w pamięci, drop, to czy bajty siedzą w arenie) są odkładane na etap mono.

2. Intuicja

Dobra wiadomość: sema już działało

Sondowanie pokazało, że zasada „T jest move-only" była już spełniona, tylko przypadkiem. Sema czyta typy z AST, a nazwany typ T nie jest nigdy Copy. Zmienne lokalne typu T trafiają do Ty::Unknown, co też nie jest Copy. Dlatego val a = move x; val b = move x jest odrzucane dla T tak samo jak dla String. Ta część PR to więc tylko fixtury, które to utrwalają.

Zła wiadomość: luka w escape

Moduł escape pyta o typ wartości: uses_arena_storage(ty), czyli „czy bajty leżą w arenie?". Dla String i klas odpowiedź to „tak". Dla Param było „nie", więc escape traktował T jak niewinny skalar i pomijał swoje reguły.

fun id<T>(var x: T): T {
    return move x        // przed zmianą: przechodziło dla T
}

Dla String ta sama linia jest odrzucana („returning a moved or promoted String is not supported yet"). Po monomorfizacji id<String> by się więc nie skompilowało, mimo że generyczna wersja została zaakceptowana. To dokładnie złamanie INV-10.

Przed mono

id<T>return move xzaakceptowane
→

Po mono, T = String

id<String>return move xodrzucone

Rozwiązanie: oceniaj T jak jego najostrzejszą instancję

Nie wiemy, czym będzie T, więc zakładamy najgorszy przypadek dla tych reguł: String (bajty w arenie, brak Copy). Jeśli ciało przechodzi przy takim założeniu, przejdzie też dla i32, klasy i Ref<Klasa>, bo te nie są od niego bardziej restrykcyjne.

Cena jest oczywista: to podejście konserwatywne. Ciało, które byłoby poprawne dla i32, ale łamie reguły dla String, zostanie odrzucone, bo generyczne T nie zna swojej instancji. Pełna precyzja wymaga ograniczeń (bounds), które są poza zakresem (TS-P6-01).

Dlaczego „top-level T" nie wystarczy Wartość typu Ref<T> albo Vec<T> też zależy od nieznanego T. Dlatego decyzję „czy to może być w arenie" podejmuje has_param, które szuka Param w całym typie, a nie tylko na wierzchu. Natomiast reguła „zwracanie przeniesionego napisu" dotyczy tylko wartości, która sama jest T (is_param), bo tylko wtedy może być napisem.

Skąd wiemy, że to działa? Test różnicowy

Bez monomorfizacji nie da się sprawdzić „po mono" w kompilatorze, więc test robi to tekstowo: bierze generyczne ciało, podstawia za T kolejno i32, String, P i Ref<P> i sprawdza każdą wersję zwykłym frontendem. Reguła: jeśli wersja generyczna jest zaakceptowana, wszystkie cztery instancje też muszą być. Dodatkowo, jeśli generyczna jest odrzucona, to przynajmniej jedna instancja musi być odrzucona (odrzucenie nie może być bezpodstawne).

Znaleziona przy okazji luka (poza zakresem): #138 Test ujawnił, że typeck akceptuje Vec<T> i Ref<T> przed mono, choć Vec<P> (klasa) i Ref<i32> są błędami typów, a nie własności. Te przypadki są w teście jawnie pominięte (skip), a sprawa jest opisana w zgłoszeniu #138.

3. Kod krok po kroku

3.1 Dwa zapytania o typ (src/ty/query.rs)

+ /// Whether `id` mentions an opaque type parameter anywhere (`Ref<T>`, `Vec<T>`, `T?`, ...).
+ pub fn has_param(&self, id: TyId) -> bool { ...visitor szukający TyData::Param... }
+
+ /// An opaque type parameter (through `?`): any concrete type may stand for it after mono.
+ pub fn is_param(&self, id: TyId) -> bool {
+     matches!(self.data(self.base(id)), TyData::Param(_))
+ }

has_param używa istniejącego TypeVisitor/walk z ty/fold.rs, więc schodzi w argumenty klas (dzięki #45), tablice, Vec, Ref i nullable. is_param sprawdza tylko wierzch (po zdjęciu ?).

3.2 Rdzeń: maybe_arena (src/escape.rs)

+ /// Whether a value of `ty` may live in an arena. An opaque `T` is judged as its most
+ /// restrictive instantiation (`String`), so a generic body accepted here stays accepted for
+ /// every instance (RFC 0002 section 4).
+ fn maybe_arena(&self, ty: TyId) -> bool {
+     self.tcx.uses_arena_storage(ty) || self.tcx.has_param(ty)
+ }

Wszystkie osiem dotychczasowych wywołań self.tcx.uses_arena_storage(...) w tym pliku zamieniono na self.maybe_arena(...). To jedyna zmiana logiki: gdzie escape pytał „czy to w arenie?", teraz dla T dostaje „możliwe, że tak". Dotyczy to zwracania z wewnętrznego regionu, przypisań na zewnątrz, wartości gałęzi if, indeksowania i operacji na wektorach.

Druga zmiana: predykat „przeniesiony lub awansowany napis" przy zwracaniu.

HirExprKind::Ident { use_kind: UseKind::Move | UseKind::Promote, .. }
    if self.tcx.is_string(expr.ty) || self.tcx.is_param(expr.ty)

Zwróć uwagę, że tu użyto is_param, a nie has_param: sama wartość musi być T, żeby mogła okazać się String.

3.3 Czytelne komunikaty (param_note)

Komunikaty escape mówią o String, więc użytkownik generycznej funkcji mógłby się zdziwić. Jeden helper dopisuje wyjaśnienie, gdy typ zawiera parametr:

fn param_note(&self, ty: TyId) -> &'static str {
    if self.tcx.has_param(ty) {
        " (a type parameter is judged as its strictest instance, `String`)"
    } else { "" }
}

Notatka trafia do czterech komunikatów: wartość gałęzi if, zwracanie z wewnętrznego regionu, przypisanie na zewnątrz i zwracanie przeniesionego napisu. W komunikacie o zwracaniu nazwa typu T0 (nazwy parametrów są już wtedy zresetowane) została zastąpiona słowami „generic value". Komunikaty dla zwykłych typów nie zmieniły się ani o znak.

3.4 Test różnicowy (tests/generic_ownership.rs)

  • instantiate podstawia T jako identyfikator (nie wewnątrz dłuższych nazw jak Tree ani w literałach napisowych) i usuwa <T> z deklaracji fun, także metod.
  • CASES to lista przypadków z flagą „oczekiwana akceptacja" i opcjonalną listą pominiętych instancji. Przypadki zaakceptowane: tożsamość, wywołanie przez inną funkcję, gałęzie, kopia val, przeniesienie do zmiennej, zagnieżdżone Ref<T>, metoda generyczna. Przypadki odrzucone: return move x, to samo w gałęzi, przypisanie z wewnętrznego regionu, wartość if z move, podwójne przeniesienie.
  • Dwa testy: „zaakceptowane generyczne ⇒ zaakceptowane dla każdej instancji" oraz „odrzucone generyczne ⇒ odrzucone dla jakiejś instancji".

  • Pliki złote zmieniły się tylko o dodane fixtury: 39 linii dodanych, zero zmienionych, więc istniejące wyniki escape pozostały bez zmian.
  • docs/memory-model.md: nowa sekcja „Generic bodies (pre-mono)". RFC 0001 dostało notatkę „Implementation (#46)". W RFC 0002 INV-10 przestało być „n/a".
Czego ten PR nie robi Nie dodaje debug_assert w kompilatorze: bez monomorfizacji nie ma gdzie go podpiąć, więc gwarancja „po mono" jest tak mocna, jak tekstowa instancjacja w teście. Wewnątrzkompilatorowe sprawdzenie każdej instancji czeka na #47. Nie obsługuje też ograniczeń (bounds), więc wynik jest konserwatywny.

4. Quiz

Pięć pytań. Kliknij odpowiedź, a dostaniesz informację zwrotną.

1. Dlaczego fun id<T>(var x: T): T { return move x } przechodziło przed tą zmianą, choć id<String> jest odrzucane?

Sema działało poprawnie (T jest move-only). Luka była w escape: uses_arena_storage jest fałszem dla Param, więc T był traktowany jak niewinny skalar.

2. Dlaczego rozwiązaniem jest ocena T jak String, a nie jak i32?

Chodzi o gwarancję „zaakceptowane przed mono ⇒ zaakceptowane dla każdej instancji". Wystarczy założyć najgorszy przypadek. Ceną jest konserwatyzm: niektóre ciała poprawne dla i32 zostaną odrzucone.

3. Po co dwa zapytania, has_param i is_param, skoro oba szukają parametru typu?

Wartość typu Ref<T> zależy od T, więc musi być traktowana ostrożnie (has_param). Ale „przeniesiony lub awansowany napis" to wartość, która jest sama napisem, więc musi być wprost T (is_param).

4. Test różnicowy pomija Vec<T> dla P i Ref<T> dla i32. Dlaczego to jest uczciwe, a nie ukrywanie problemu?

Typeck akceptuje Vec<T> i Ref<T> przed mono, mimo że Vec<P> i Ref<i32> są nieprawidłowymi typami. To osobny problem. Pominięcie jest widoczne w kodzie testu, a nie ukryte.

5. Na jakiej podstawie PR twierdzi, że ciało przyjęte przed mono przejdzie po mono, skoro monomorfizacji w kompilatorze nie ma?

Dowodu formalnego nie ma, a debug_assert nie został dodany, bo nie ma gdzie go podpiąć. Gate blokuje generowanie kodu, ale nie dowodzi niczego o własności. Gwarancja jest więc tak mocna, jak ten harness.
