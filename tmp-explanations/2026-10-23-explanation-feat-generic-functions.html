1. Tło

Dla początkujących: czym są typy generyczne i inferencja (można pominąć)

Funkcja generyczna to funkcja napisana raz dla wielu typów. Zamiast osobno pisać idI32(x: i32) i idString(x: String), piszemy:

fun id<T>(x: T): T {
    return x
}

T to parametr typu: zmienna, której wartością jest typ. Przy wywołaniu id(1) kompilator ustala, że T = i32, a przy id("s"), że T = String.

Są dwa sposoby sprawdzania takiej funkcji. Pierwszy to szablon (jak w C++): ciało sprawdzamy dopiero po podstawieniu konkretnego typu, osobno dla każdego użycia. Drugi to sprawdzenie raz (jak w Rust czy Javie): ciało sprawdzamy jeden raz, traktując T jako nieznany, nieprzezroczysty typ. Bork wybiera drugi, więc w ciele funkcji nie wolno zrobić z T niczego, co zakładałoby coś o jego naturze (dodać dwóch T, odwołać się do pola).

Inferencja to zgadywanie typów, których programista nie napisał. Technicznie: dla nieznanego typu tworzymy zmienną inferencji (?0), a potem unifikujemy ją z tym, co z kodu wynika. Na koniec każda zmienna powinna mieć wartość.

Co już było w Bork przed tą zmianą

Type checker Bork (katalog src/typeck) pracuje na interningowanych typach TyId, opisanych przez TyData. Warianty istotne tutaj to Param(ParamIdx) (parametr typu) i Infer(InferVar) (zmienna inferencji). Do tej pory zmienne inferencji służyły tylko do literałów: 1 dostaje zmienną rodzaju Int, a 1.5 rodzaju Float. Na końcu ciała funkcji default_literals zamienia niezwiązane zmienne na i32 i f64.

Poprzednie PR-y budowały grunt pod generyki:

  • #42: parser rozumie fun f<T>, Box<i32> i turbofish f::<i32>(x).
  • #43: deklaracje generyczne są walidowane (duplikaty, cienie, arność) i trafiają do HIR jako typy Param, ale ciała nie były sprawdzane. Funkcja z <T> szła przez generics::declaration_only.
  • #38–#41: InferCtxt z unifikacją, bidirectional synthesize/check i zasada „żadna zmienna nie dociera do HIR".

Efekt: parser i walidator znały generyki, ale każdy program z generyczną funkcją był odrzucany z komunikatem „not supported yet". Ten branch zdejmuje to ograniczenie dla funkcji najwyższego poziomu.

2. Intuicja

Zmiana składa się z dwóch ruchów, które odpowiadają dwóm stronom każdej funkcji generycznej: jej ciału i jej wywołaniom.

Ruch pierwszy: ciało sprawdzamy raz, z nieprzezroczystym T

Wewnątrz fun id<T>(x: T): T typ T to Param(0). Wartość tego typu można przekazać dalej, zwrócić albo zapisać, bo do tego nie trzeba wiedzieć, czym jest T. Nie można jej natomiast dodać, porównać przez == ani odczytać jej pola, bo nie wiemy, czy T to liczba. Bork nie ma jeszcze ograniczeń (bounds, jak T: Add), więc komunikat błędu mówi to wprost:

fun double<T>(x: T): T {
    return x + x
}
// arithmetic operands must have the same numeric type, got T and T;
// a type parameter has no bounds yet, so operators and members need a bound (not supported yet)

Ruch drugi: wywołanie podstawia świeże zmienne za parametry

Przy id(1) checker bierze sygnaturę (x: T) → T i zastępuje każde T świeżą zmienną inferencji ?0. Powstaje sygnatura tego jednego wywołania: (x: ?0) → ?0. Argumenty, typ oczekiwany albo jawny turbofish ustalają potem, czym jest ?0.

1. Sygnatura

id<T>(x: T): T
→

2. Świeża zmienna

T ↦ ?0 (General)(x: ?0): ?0
→

3. Argument 1

?0 ~ ?int?0 staje się Int
→

4. Koniec ciała

default_literals?0 := i32

Skąd bierze się wartość zmiennej? Trzy możliwe źródła, w kolejności, w jakiej działają:

ŹródłoPrzykładRezultat
jawne argumenty (turbofish)id::<i64>(1)nie powstaje zmienna; T := i64, a literał 1 musi pasować do i64
typ oczekiwany (podpowiedź)val b: i64 = id(2)zwracany ?0 unifikowany z i64 przed czytaniem argumentów

nicmake() dla make<T>(): Tbłąd cannot infer type parameter `T` of `make`
Nowy rodzaj zmiennej: General Zmienne literałowe (Int, Float) mają domyślny typ, więc nigdy nie zostają „puste". Zmienna parametru typu nie ma żadnego domyślnego typu, więc dostała nowy rodzaj VarKind::General. Jeśli General zunifikuje się z Int, wynikiem jest Int (reguła w src/infer/unify.rs:65). Dlatego id(1) kończy jako i32.

Co z błędami „nie da się wywnioskować"?

Po domyślnym uzupełnieniu literałów checker przegląda listę „oczekujących" parametrów (Env::pending). Jeśli któraś zmienna nadal jest niezwiązana, zgłasza błąd i od razu zatruwa ją typem Error. Dzięki temu zależne od niej wyrażenia nie sypią kaskadą kolejnych komunikatów.

Czego ten branch celowo nie robi

  • Nie generuje kodu. Bez monomorfizacji nie ma jak skompilować id. codegen_gate odrzuca więc generyczne funkcje przy bork build, ale check je akceptuje.
  • Nie obsługuje generycznych metod i klas. Zostają „declaration-only". Wywołanie generycznej metody daje błąd „not supported yet".
  • Nie ma ograniczeń (bounds). Dlatego operatory na T są zakazane.

3. Kod krok po kroku

Zmiany grupuję według roli, a nie według plików. Idę od fundamentów (jak typ T jest reprezentowany i drukowany) do tego, co widać z zewnątrz (wywołania i komunikaty).

3.1 Reprezentacja: nazwy parametrów i rodzaj zmiennej

src/ty/mod.rs, src/ty/print.rs, src/ty/sig.rs

  • TyCtx dostał pole param_names i metodę set_param_names. Dzięki temu TyPrinter drukuje Param(0) jako T, a nie T0. Poza funkcją generyczną lista jest pusta, więc zachowuje się jak dawniej.
  • FnSig dostał generic_names, bo przy wywołaniu potrzebujemy nazw parametrów do komunikatów (cannot infer type parameter `T`).
  • Komentarz przy TyData::Param przestał twierdzić, że parametr „nigdy nie trafia do HIR". Teraz trafia, ale tylko w funkcjach generycznych.
pub struct FnSig<T> {
    pub generics: Vec<ParamIdx>,
    + pub generic_names: Vec<String>,
    pub params: Vec<T>,
    pub ret: T,
}

3.2 Włączenie sprawdzania ciała

src/typeck/mod.rs, funkcja check_function:

- if !generics.is_empty() {
+ // Methods stay declaration-only; top-level generic functions are checked with `T` opaque.
+ if owner.is_some() && !generics.is_empty() {
      return generics::declaration_only(...);
  }
+ tcx.set_param_names(generics.clone());
  let mut env = Env::new(...);
+ env.tparams = generics::scope(&[], &function.generics);

To jest sedno: wcześniej każda funkcja z <T> wychodziła tu wcześnie jako „tylko deklaracja". Teraz wychodzą tak tylko metody. Funkcje najwyższego poziomu przechodzą pełną ścieżkę. env.tparams mapuje nazwę T na ParamIdx, więc Env::lower potrafi zamienić napisany w ciele typ T (np. val y: T = x) na Param. Wcześniej przekazywało tu puste &[].

Na końcu funkcji set_param_names(Vec::new()) sprząta, żeby nazwy nie wyciekły do następnej funkcji. collect_fun_sigs i collect_method_sigs wypełniają nowe generic_names.

3.3 Instancjacja wywołania

src/typeck/expr/call.rs, nowa funkcja instantiate. Ma trzy gałęzie:

let args: Vec<TyId> = if type_args.is_empty() {
    // brak turbofisha: świeża zmienna General na każdy parametr + wpis do env.pending
    sig.generic_names.iter().map(|param| { ... }).collect()
} else if type_args.len() != sig.generics.len() {
    // "`id` expects 1 type argument, got 2"
    return None;
} else {
    // turbofish: zamień napisane typy na TyId
    type_args.iter().map(|ty| env.lower(ty, Some(span))).collect()
};
// podstaw args za Param w parametrach i w typie zwracanym
let params = sig.params.iter().map(|&ty| subst(env.tcx, ty, &args))...

Funkcja subst istniała od #34. Może się nie powieść, gdy podstawienie dałoby T?? (np. T := i32? w miejscu, gdzie sygnatura ma już T?). Ten przypadek daje osobny błąd „would make a nullable of a nullable".

callee_signature przyjmuje teraz type_args i woła instantiate. W check_call dochodzą dwie rzeczy:

  • Podpowiedź z typu oczekiwanego. Dla generycznej funkcji wykonujemy env.same(call_return_ty, expected) przed sprawdzeniem argumentów. To tylko podpowiedź: nieudana unifikacja nic nie zmienia, a rozbieżność zgłosi wołający. Dlatego dispatch przekazuje teraz expected do check_call.
  • Walidacja turbofisha. f::<i32>(1) dla niegenerycznego f daje „`f` is not generic; it takes no explicit type arguments". Pomocnicza is_generic_fn sprawdza, że nazwa to rzeczywiście funkcja użytkownika, a nie metoda ani klasa, które mogłyby ją zasłaniać.

Ta walidacja zastąpiła stary blok w expr/mod.rs, który odrzucał każdy turbofish komunikatem „not supported yet". Dlatego w dispatch ubyło 10 linii.

3.4 Koniec ciała: zmienne bez wartości

src/typeck/env.rs definiuje PendingParam { var, span, callee, param }. src/typeck/mod.rs dodaje report_uninferred, wołane zaraz po default_literals:

for pending in std::mem::take(&mut env.pending) {
    let ty = env.infcx.resolve_shallow(env.tcx, pending.var);
    if !matches!(env.tcx.data(ty), TyData::Infer(_)) { continue; }   // ustalone: OK
    env.error("cannot infer type parameter `{param}` of `{callee}`; specify it explicitly, ...", span);
    // zatruj, żeby zależne wyrażenia milczały
    let _ = env.infcx.unify(env.tcx, ty, env.tcx.error());
}

Zmieniło się też settle w check_function. Stary kod robił unwrap_or(ty) przy rozwiązywaniu zmiennej. Nowy obsługuje błąd (nullable nullable'a) i raportuje go, zamiast po cichu go ignorować.

3.5 Skutki uboczne nowego rodzaju zmiennej

src/typeck/env.rs:

  • show (używane w komunikatach) dla niezwiązanej zmiennej General drukuje samą zmienną, zamiast zgadywać i32. Wcześniej każda niezwiązana zmienna szła do i32.
  • is_numeric przestało traktować każdą niezwiązaną zmienną jak liczbę. Teraz General nie jest numeryczna. Bez tego x + y na jeszcze nieustalonym typie przechodziłoby bez błędu.

3.6 Nieprzezroczyste T i podpowiedź o ograniczeniach

Dwie nowe metody w Env: is_param oraz bounds_hint, która zwraca dopisek „; a type parameter has no bounds yet, ..." tylko wtedy, gdy któryś z typów w błędzie jest parametrem. Dopisek doklejają: arytmetyka i porównania (binary.rs), nieznane pole (field.rs) oraz wywołanie metody na T (method.rs).

Najciekawsza jest równość w binary.rs. Dotąd a == b przechodziło dla dwóch wartości tego samego typu. Dla T == T to samo sprawdzenie by przeszło, więc dodano flagę opaque, która wymusza błąd:

let opaque = env.is_param(lhs_ty) || env.is_param(rhs_ty);
if !poisoned && (opaque || (!same(...) && !(both text))) { /* błąd */ }

Komunikat nadal mówi „must have the same type, got T and T", co brzmi dziwnie, ale dopisek o ograniczeniach wyjaśnia, o co chodzi.

4. Quiz

Pięć pytań. Kliknij odpowiedź, a dostaniesz informację zwrotną.

1. Dlaczego fun double<T>(x: T): T { return x + x } jest odrzucane już przy samym sprawdzaniu ciała?

Ciało sprawdzane jest raz, z T jako Param. Ten branch właśnie włączył to sprawdzanie (pierwsza odpowiedź opisuje stan sprzed zmiany). Brak wywołania nie ma znaczenia, a dodawanie działa dla wszystkich liczb, nie tylko i32.

2. Co dzieje się z parametrem T w sygnaturze id<T>(x: T): T, gdy napiszemy id("s") bez turbofisha?

Zmienna powstaje w instantiate, a unifikacja z argumentem robi resztę. Kopiowanie ciała to model szablonów (C++), którego Bork nie używa. Turbofish jest opcjonalny, gdy da się wnioskować.

3. Po co wołane jest env.same(call_return_ty, expected) przed sprawdzeniem argumentów w val b: i64 = id(2)?

To podpowiedź (hint). Nieudana unifikacja nic nie zmienia, a rozbieżność typów zgłosi wołający. Argumenty nadal są sprawdzane.

4. Program: fun make<T>(): T { return make() } oraz fun main() { make() }. Dlaczego wywołanie w main jest błędem?

Zmienna wpada do env.pending, a report_uninferred po default_literals znajduje ją wciąż niezwiązaną. Komunikat podpowiada make::<..>(). Zmienna General nie ma typu domyślnego, w przeciwieństwie do literałów.

5. Co zrobi bork build dla poprawnego programu z funkcją id<T>?

Ten branch dodaje tylko sprawdzanie typów. Generowanie kodu (monomorfizacja) to osobna, przyszła praca, więc codegen_gate blokuje takie funkcje. Przed zmianą odrzucał je sam checker, teraz robi to dopiero gate.
