1. Tło

Stan przed zmianą

Ticket #49 nauczył kompilator rozumieć enumy: składnię, typy, konstrukcję wariantu (Shape.Rect(2, 3)) i generyki. Ale backend (LLVM) ich nie znał. Brama kodegenu (src/codegen_gate.rs) odrzucała każdy program, w którego typach pojawił się enum, komunikatem enums are not supported by codegen yet. W src/memory.rs konstrukcja enuma była traktowana „zachowawczo”, bo i tak nie dało się jej zbudować.

Jedyne dane o enumach w HIR to były wyrażenia (EnumConstruct) i typy (TyData::Enum). Nie było definicji enuma: HirProgram miał tylko classes i functions. Backend nie miał skąd wiedzieć, jakie są warianty i jakie pola.

Cel #52Zbudować, trzymać w pamięci i sprzątać wartości enumów w natywnym kodzie. Poza zakresem: when na enumach (czytanie wartości z powrotem), czyli #53 i #54.

2. Intuicja

Ruch pierwszy: enum to szuflada z karteczką

Wartość enuma to jeden z wariantów naraz. W pamięci to jeden slot: najpierw tag (liczba mówiąca, który wariant), potem dane tego wariantu. Wszystkie wartości danego enuma muszą mieć ten sam rozmiar, więc slot ma rozmiar największego wariantu.

Empty

tag=0(reszta pusta)

Flag(on: bool)

tag=1on

Rect(w: i32, h: i64)

tag=2wh

Slot dla całego enuma = rozmiar Rect (16 bajtów, wyrównanie 8). Bez oszczędzania miejsca: takie sztuczki (niche optimization) są poza zakresem.

Ruch drugi: mono potrzebuje definicji, żeby zrobić instancje

Dla Maybe<T> trzeba osobnego układu na Maybe<i32> i na Maybe<String>. Skoro generyczne klasy mają HirClass, enumy dostają HirEnum i przechodzą tę samą monomorfizację.

Ruch trzeci: pola enuma są własnością jak pola klasy

String i tablice są kopiowane do areny enuma. Ref nie jest kopiowany bit po bicie: licznik referencji musi wzrosnąć przy budowie i spaść przy sprzątaniu. Dlatego wspólny kod dla pól klas i payloadów (store_owned_field).

Ruch czwarty: sprzątanie zależy od tagu

Wariant One(a: Ref<Node>) trzyma Ref zaraz po tagu, Two(t: i8, a: Ref, b: Ref) dalej. Sprzątanie musi wiedzieć, który wariant jest w środku. Kompilator generuje funkcję, która czyta tag i zwalnia tylko Ref-y tego wariantu. Rejestruje ją raz w arenie.

Ruch piąty: brama przepuszcza enumy, ale łapie move

Przenoszenie enuma (val f = move e) jeszcze nie jest zaimplementowane. Zamiast paniki kompilatora brama zgłasza moving enum values is not supported by codegen yet.

Czego ten PR nie robi
  • Nie czyta wariantów z powrotem (when): #53/#54.
  • Debug info opisuje tylko tag, bez pól wariantów.
  • Nie zmienia narzędzia bork-debug (Python): ono czyta nazwy z rejestru runtime.
  • Nie optymalizuje rozmiaru enumów.

3. Kod krok po kroku

3.1 Definicja enuma w HIR (src/hir/mod.rs, src/typeck/mod.rs)

// HirProgram
+    pub enums: Vec<HirEnum>,

+pub struct HirEnum {
+    pub name: String,
+    pub generics: Vec<String>,
+    pub variants: Vec<HirVariant>,   // indeks = tag
+}

Typeck już miał EnumInfo (z #49). Teraz przepisuje je do HIR w kolejności deklaracji, bo indeks wariantu jest tagiem.

3.2 Monomorfizacja enumów (src/mono.rs)

+pub(crate) fn enum_instance_name(tcx: &TyCtx, ty: TyId) -> Option<String> {
+    let (def, args) = tcx.enum_args(ty)?;
+    Some(mangle(tcx.class_name(def), tcx, args))
+}

instantiate_classes stało się instantiate_types i zwraca też listę enumów. Wspólny kod podstawiania typów w polach wydzielono do instantiate_fields, żeby klasy i enumy nie miały kopii. Konstrukcje enumów dostają nazwę instancji (Maybe<i32>), pod którą backend znajdzie układ.

3.3 Układ w LLVM (src/codegen/llvm/context.rs)

fn enum_layout_of(&self, e: &HirEnum) -> Result<EnumLayout<'ctx>, String> {
    let (mut size, mut align) = (0, 1);
    for variant in &e.variants {
        let mut elements = vec![self.context.i32_type().into()];   // tag
        for field in &variant.fields { elements.push(self.basic_type(field.ty)...); }
        let ty = self.context.struct_type(&elements, false);
        size = size.max(self.target_data.get_abi_size(&ty));
        align = align.max(u64::from(self.target_data.get_abi_alignment(&ty)));
        variants.push(ty);
    }
    Ok(EnumLayout { variants, size: size.next_multiple_of(align), align })
}

Dla każdego wariantu powstaje struktura { i32 tag, pola... }. Rozmiar i wyrównanie bierzemy od LLVM (target_data), nie liczymy ręcznie. Slot = maksimum po wariantach.

Alokacja jest w arenie wyznaczonej przez plan pamięci (ta sama ścieżka co obiekty klas: begin_object_construct obsługuje teraz też EnumConstruct). Wartość to uchwyt {arena, wskaźnik}, taki jak dla klas.

store_owned_field to wydzielona część emit_object_construct: Ref idzie przez store_ref (licznik rośnie), reszta przez materialize_owned_value (kopia do areny). Parametr register_drop mówi, czy rejestrować sprzątanie pojedynczego Ref: dla klas tak, dla enumów nie, bo rejestruje się cały slot.

3.5 Sprzątanie (src/codegen/llvm/enum_glue.rs)

let tag = builder.build_load(i32_ty, tag_ptr, "tag")?;
for (index, variant) in e.variants.iter().enumerate().filter(|(_, v)| has_ref(v)) {
    // if tag == index { bork_ref_drop(&payload.field) dla każdego Ref }

Dla każdego enuma, który ma Ref w jakimś wariancie, powstaje wewnętrzna funkcja bork.drop.<Enum>. Ma łańcuch porównań z tagiem i w każdej gałęzi woła bork_ref_drop na polach Ref tego wariantu. Enumy bez Ref nie dostają nic: arena zwolni je sama.

W src/memory.rs EnumConstruct dzieli gałąź z ObjectConstruct, więc konstrukcja enuma dostaje arenę i krawędzie referencji jak obiekt. W src/ty/query.rs enum liczy się jako typ z pamięcią w arenie (uses_arena_storage, owns_result).

3.7 Ref<Enum> i debug

W src/typeck/expr/mod.rs wartość enuma może teraz zamienić się w Ref do tego enuma (wcześniej tylko klasy). W src/codegen/llvm/debug/types.rs enum dostaje nazwę bork::Object<E> i opis slotu bork::Payload<E> (tylko tag).

4. Quiz

Wynik: 0 / 0 (z 7)

1. Jak Bork trzyma wartość enum Shape { Empty, Rect(w: i32, h: i64) } w arenie?

Slot zaczyna się od tagu (i32), a po nim idą pola wybranego wariantu. Tag to indeks wariantu w kolejności deklaracji.

2. Warianty mają ładunki 4, 16 i 24 bajty. Ile bajtów alokuje Bork dla każdej wartości tego enuma?

Slot musi pomieścić każdy wariant, więc ma rozmiar i wyrównanie największego. Test układu sprawdza, że trzy różne warianty alokują to samo.

3. Dlaczego do #52 potrzebny był HirEnum?

Bez definicji w HIR codegen nie ma skąd wziąć listy wariantów, ich kolejności (tagów) ani typów pól. Mono też potrzebuje definicji generycznej, żeby zrobić z niej instancje.

4. Dlaczego pole Ref w wariancie nie jest kopiowane bit po bicie?

Kopia bitowa nie zwiększyłaby licznika, więc obiekt mógłby zniknąć za wcześnie albo zostać na zawsze. Dlatego Ref idzie przez store_ref, jak pola klas.

5. Enum ma One(a: Ref<Node>) i Two(t: i8, a: Ref<Node>, b: Ref<Node>). Co robi funkcja sprzątająca?

Pole a leży w różnych miejscach w obu wariantach. Zwolnienie po złym wariancie czytałoby śmieci, więc funkcja przełącza się po tagu. Arena sama nie zmniejszy liczników referencji.

6. Po co strongCount w programach programs/build/enums?

Wyciek zostawia licznik wyższy po powrocie, nadmierne zwolnienie niższy. Test porównuje licznik przed i po.

7. val f = move e, gdzie e jest enumem. Co robi kompilator po #52?

Wcześniej to kończyło się paniką kompilatora. Teraz brama odrzuca przeniesienie z komunikatem; samo przenoszenie wróci razem z lowerowaniem when.
