Jak wygląda MIR: typy, drukarka i weryfikator

Wyjaśnienie PR #234 (branch feat/66-mir-types, krok M2a z RFC 0006, część #66): dane MIR, zapis tekstowy, weryfikator v0 i uzgodnienie tabeli operacji z kodem runtime. Nic jeszcze nie buduje MIR z programu.

1. Tło

Dla początkujących: czym jest MIR i graf przepływu (można pominąć)

Kompilator zwykle tłumaczy program przez kilka języków pośrednich. MIR to taki język: prostszy od drzewa składni, bliższy maszynie. Funkcja jest w nim podzielona na bloki. Każdy blok to ciąg prostych instrukcji i jedna instrukcja końcowa (skok, wywołanie, powrót). Połączone skokami bloki tworzą graf przepływu sterowania (CFG). Dzięki temu pętle, break i return są po prostu krawędziami w grafie.

bb0

region_enter r0 x = ...
→

bb1 (pętla)

region_reset r0
→

bb2

region_exit r0 return

Stan przed zmianą

RFC 0006 przenosi decyzje o własności, regionach i układzie z wielu przejść po HIR oraz z emisji LLVM do jednego MIR. Krok M1 (#232) dał moduł układu typów. Brakowało samego MIR: jego typów, sposobu na obejrzenie go i sprawdzenia, że jest poprawny.

Cel M2aZdefiniować typy MIR, ich zapis tekstowy i weryfikator, oraz uzgodnić listę operacji w RFC z tym, co naprawdę robi runtime. Budowanie MIR z HIR (build.rs) i flaga --emit-mir to osobny PR (M2b).

2. Intuicja

Operacje, które mówią, w której arenie działają

Najważniejsza zmiana względem dzisiejszego kodu: każda operacja, która alokuje, nazywa arenę wprost (ArenaRef), zamiast polegać na ukrytym stosie „bieżącej areny” w emiterze. Dzięki temu analizy mogą czytać, gdzie co leży, bez uruchamiania emisji.

RodzinaPrzykłady
ObliczeniaAssign(place, Binary / Aggregate / Len / Slice)
Pamięć i arenyAlloc, CopyInto, Promote, ArenaCreateDynamic, RegisterDrop
Referencje RefCreate, Clone, MoveOut, Store, Rehome, Drop, Count, IsNone
RegionyRegionEnter, RegionExit, RegionReset
Zakończenia blokówGoto, Switch, Match, Call, Return, Unreachable, Abort

Zaskoczenie z czytania runtime'u: reset areny zwraca nową arenę

Funkcja bork_arena_reset niszczy arenę i zwraca nowy token. Gdyby MIR traktował region jako stałą, wyjście z pętli zwalniałoby nieaktualną arenę. Dlatego arena regionu jest w MIR lokalem (RegionArena), a RegionReset go przypisuje na krawędzi powrotnej pętli.

wejście

region_enter r0
→

krawędź powrotna

_2 = region_reset r0
→

wyjście

region_exit r0 (pop najnowszego _2)
Tylko gdy działaWeryfikator na razie sprawdza, że region_reset jest wewnątrz swojego regionu i zapisuje do lokala RegionArena. Pełne sprawdzenie, że żadna ścieżka nie zwalnia nieaktualnego tokenu, wymaga prawdziwych ciał z build.rs.

Weryfikator: jedna zgodna historia na każdej ścieżce

Weryfikator chodzi po grafie w głąb i do każdego bloku dochodzi z pewnym stanem: stosem otwartych regionów i zbiorem żywych tymczasowych Ref. Jeśli dwie ścieżki dochodzą do jednego bloku z różnym stanem, to błąd. Każdy tymczasowy Ref musi być zdefiniowany i zużyty dokładnie raz (zapisany, przeniesiony, przeniesiony do nowego właściciela albo zwolniony).

3. Kod krok po kroku

1. RFC 0006, sekcja 3.2.2

Wynik czytania bork_runtime i hooków debug: dodane RefIsNone, powody Abort, osobne zrzucanie obserwacji (nie jako wariant DropGlue), pola DebugLabel oraz uwaga, że StorageLive/Dead ma skutki w runtime i musi być na każdej krawędzi wyjścia.

2. src/mir/body.rs

Dane: Local, Place z projekcjami, Operand (Copy/Move/Reborrow/Const), ArenaRef, StmtKind, TermKind, MirPat, Body. Metody walk wyliczają, jakie lokale, operandy i areny dana instrukcja dotyka, żeby weryfikator i przyszłe analizy nie powtarzały tej listy.

3. capability.rs

Dziewięć nazw konstrukcji, których MIR jeszcze nie obsługuje (closure, match-ref, pat-presence, move-aggregate, field-access, safe-field-enum, indirect-call, unit-elem, unit-payload-bind). Przyszła brama będzie pytać o nie zamiast trzymać listę odrzuconych kształtów.

4. print.rs i verify.rs

fn f (parent=false, sink=false) {
  let _0: i32 [Return]
  let _1: Ref<i32> [Temp]
  region r0 Block
  bb0:
    region_enter r0
    _1 = ref_create source=current target=root 0
    ref_drop move _1
    region_exit r0
    return
}

Drukarka pomija spany, żeby zmiana w nieistotnym fragmencie źródła nie zmieniała złotych plików. Weryfikator zwraca listę błędów (verify) albo panikuje jako wewnętrzny błąd kompilatora (verify_or_panic).

Czego jeszcze nie maNie sprawdza przepływu inicjalizacji i przeniesień, zawierania się czasu życia areny ani parowania StorageLive i StorageDead. Typy są sprawdzone tylko na ciałach budowanych ręcznie w testach i mogą się zmienić przy build.rs.

4. Quiz Wynik: 0 / 0 (z 5)

1. Dlaczego każda operacja alokująca w MIR nazywa arenę wprost (ArenaRef)?

Dziś wybór areny jest dynamicznym stanem emitera (zapisz i przywróć). W MIR jest jawnym operandem, więc weryfikator i analizy widzą go w danych.

2. Co zmieniło się w modelu RegionReset po przeczytaniu runtime'u?

Gdyby arena była stałą, wyjście z pętli zwalniałoby nieaktualny token. Dlatego jest lokal RegionArena, a RegionExit zwalnia najnowszą wartość.

3. Weryfikator dochodzi do bloku dwiema ścieżkami: jedna otworzyła region r0, druga nie. Co robi?

Regiony muszą się zagnieżdżać na każdej ścieżce, więc stan przy łączeniu musi być zgodny. To może odrzucić poprawne ciała z build.rs, co sprawdzi dopiero M2b.

4. Co oznacza reguła „tymczasowy Ref zużyty dokładnie raz”?

Dzięki temu weryfikator wyłapie podwójne zwolnienie i wyciek referencji, dwa błędy, które dziś pilnują testy runtime.

5. Po co capability.rs, skoro nic jeszcze nie używa tych nazw?

RFC 3.8 i 3.10: jedno źródło prawdy o tym, co da się zbudować. Test pilnuje, żeby identyfikatory zgadzały się z tabelą w RFC.
