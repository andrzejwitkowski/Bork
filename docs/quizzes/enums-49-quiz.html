1. Tło

Dla początkujących: enum z danymi i typ sumy (można pominąć)

Zwykły enum to lista nazwanych wartości (czerwony, zielony, niebieski). Enum z danymi (typ sumy, ADT) idzie dalej: każdy wariant może nieść własne pola.

enum Shape {
    Circle(r: f64),
    Rect(w: f64, h: f64),
    Empty
}

Wartość typu Shape to dokładnie jeden z tych wariantów: albo koło z promieniem, albo prostokąt z bokami, albo nic. Dzięki temu da się opisać drzewo, listę czy wynik, który bywa błędem, bez wartości „puste pole".

Wariant tworzy się zapisem Shape.Circle(1.0). Kompilator musi umieć sprawdzić, że do Circle trafia jedna liczba, a do Rect dwie, i że typ wyniku to Shape.

Stan przed zmianą

Bork miał klasy (rekordy z polami), generyki dla funkcji i klas (#44, #45) oraz sprawdzanie instancji (#145). Nie było żadnej konstrukcji sumy. Some i None były osobnymi wyrażeniami w AST, działającymi tylko na T?, a when umiało dopasować wyłącznie Some(name) i None.

Ticket #49 to pierwszy krok fazy „ADT i wzorce": zadeklarować enum (również generyczny) i bezpiecznie typowo skonstruować jego wariant. Dopasowanie wzorców, układ w pamięci i codegen to osobne tickety (#50–#53).

2. Intuicja

Zmiana składa się z pięciu ruchów. Każdy odpowiada jednej decyzji z audytu zapisanego w tickecie.

Ruch pierwszy: enum to osobny rodzaj typu

Zapis w kodzieTyp
Point (klasa)Class(Point, [])
Shape (enum)Enum(Shape, []) nowy
Tree<i32> (enum generyczny)Enum(Tree, [i32])

Nie użyliśmy Class, bo około 25 miejsc zakłada, że typ użytkownika to rekord z polami. Dla enuma record_def i class_def zwracają None: nie ma dostępu do pól. Co ważniejsze, TyData::children ma gałąź _ => Vec::new(). Bez jawnego ramienia dla Enum argumenty enuma po cichu znikałyby z walk, has_param i mono.

Ruch drugi: jedna przestrzeń nazw i warianty jako definicje

W DefTable klasa, enum, funkcja i stała dzielą nazwę. Warianty to osobne definicje (DefKind::Variant) z właścicielem-enumem, jak metody w klasie.

ProgramWynik
class Foo + enum Foobłąd enum koliduje z innym typem
enum E { A, A }błąd duplikat wariantu
enum E + const Ebłąd
enum String { A }błąd nazwa typu wbudowanego

Ruch trzeci: konstrukcja wariantu jak konstruktor klasy generycznej

Shape.Circle(1.0) parsuje się już dziś jako wywołanie na dostępie do pola z identyfikatorem. Nowa ścieżka w check_call przechwytuje ten kształt przed dispatchem metod i pól, jeśli lewa strona jest nazwą enuma, a żadna zmienna jej nie przesłania.

Tree<?0>pole v: ?0

2. Typ oczekiwany

Wynik

Diagnostyki: zła liczba argumentów, zły typ pola, nieznany wariant, brak możliwości wywnioskowania T. Wynikiem jest nowy węzeł HIR EnumConstruct.

Ruch czwarty: walidator układu zagląda do wariantów

Odrzucone

enum List { Nil, Cons(h: i32, t: List) }List -> List
≠

Poprawne

enum List { Nil, Cons(h: i32, t: Ref<List>) }

validate_owned_layouts przechodzi po polach wszystkich wariantów, także mieszanych cyklach klasa ↔ enum. Ref<..> został poszerzony: akceptuje klasę lub enum, żeby drzewo mogło odwoływać się do siebie.

Ruch piąty: brama kodegenu zamyka drzwi

Backendu enumów jeszcze nie ma. Brama codegenu odrzuca każdy typ lub wyrażenie, które wspomina enum (parametry, zwracane wartości, pola klas, wyrażenia), jednym błędem na funkcję.

Wniosek z review Pierwsza wersja bramki łapała tylko samą konstrukcję E.V(..). Funkcja fun f(e: E) przechodziłaby typecheck i bramkę, a potem trafiłaby do LLVM, gdzie nie ma układu dla enuma. Stąd rozszerzenie do sygnatur i pól oraz test.
Uwaga: nowe słowo kluczowe enum jest teraz zarezerwowane. W repozytorium żaden program nie używał go jako identyfikatora, ale to zmiana zachowania. enum E {} (pusty) jest akceptowane.

Czego ten PR nie robi

  • Nie ma dopasowania wzorców ani sprawdzania kompletności (#50, #51). when, Some, None i T? są bez zmian.
  • Nie ma układu w pamięci ani codegenu (#52, #53). Mono nie tworzy instancji generycznych enumów, a EnumConstruct nie jest retargetowany.
  • Nie ma Option<T> ani Result (#54). Wariant nie może nazywać się Some/None.
  • Nie ma jawnych argumentów typu na wariancie: Tree.Leaf::<i32>() daje jeden czytelny błąd.

3. Kod krok po kroku

3.1 Składnia i AST (parser.lalrpop, ast.rs)

  • Token "enum" i reguła EnumDecl: warianty rozdzielone przecinkiem lub nową linią, opcjonalny końcowy separator.
  • Item::Enum, Enum { name, generics, variants }, Variant { name, fields }, Program::enums. Nazwa enuma jest SpannedName, więc błędy wskazują właściwy token.
  • ast_number.rs numeruje węzły enumów (test korpusu wykrył brak).

3.2 Definicje (defs.rs)

  • DefKind::Enum, DefKind::Variant, lookup_enum, lookup_variant, enums().
  • Nowe konflikty: EnumConflict, VariantDuplicate, ConstEnum. Enum jest sprawdzany względem listy klas w programie (klasy rejestrują się później).
  • Odrzucony enum nie wpisuje swoich wariantów do tabeli, więc jedna pomyłka to jeden błąd.

3.3 Typy (ty/*, infer/unify.rs, mono.rs)

  • TyData::Enum(DefId, Vec<TyId>) z ramionami w children, super_fold, drukowaniu, unifikacji, bind w mono i id_to_ast w sema.
  • TyCtx::enum_ty i enum_args; managed_ref_target_ok akceptuje także enum.

3.4 Lowering i walidacja (typeck/lower.rs, generics.rs, mod.rs)

  • lower_class rozstrzyga nazwę jako klasę albo enum; build_enums typuje pola wariantów (duplikaty pól, referencje w payloadzie).
  • Parametr typu nie może nazywać się jak enum.
  • validate_owned_layouts przyjmuje tablice klas i enumów oraz raportuje cykl dla każdego rodzaju.

3.5 Konstrukcja wariantu (typeck/expr/object.rs, call.rs, mod.rs)

  • variant_path rozpoznaje E.V, gdy E to enum, nie ma przesłaniającego bindingu i nie ma ?..
  • check_variant (przyjmuje CallSite) sprawdza arność i typy pól; instantiate_field jest wspólny z konstruktorem klasy.

3.6 HIR i konsumenci (hir/*, region_walk.rs, escape.rs, memory.rs)

  • HirExprKind::EnumConstruct { enum_name, variant, fields } z ramionami w numeracji, resolve i przejściach regionów.

3.7 Brama kodegenu (codegen_gate.rs)

  • mentions_enum rekurencyjnie sprawdza typ; błąd raz na funkcję oraz dla pól klas. Pozostałe fragmenty LLVM dostały tylko unreachable! dla EnumConstruct.

3.8 Testy i dokumentacja

  • Parser, jednostkowe testy typów i unifikacji, typeck/tests/enums.rs, korpus programs/check/enums i programs/check_fail/enums (po przebłogosławieniu trzech snapshotów).
  • docs/language.md: sekcja „Enums", słowo zarezerwowane, uwaga o Ref.
  • Nie uruchomiono cargo test --features codegen (brak LLVM 23 w środowisku autora).

4. Quiz

Siedem pytań. Kliknij odpowiedź, a dostaniesz informację zwrotną.

1. Dlaczego enum dostał własny wariant TyData::Enum, zamiast używać Class?

Jawny wariant sprawia, że brakujący arm w match wywala kompilację albo jest widoczny w przeglądzie, zamiast po cichu ukrywać argumenty przed walk, has_param i mono.

2. Który zapis przejdzie typecheck dla enum Tree<T> { Leaf, Node(l: Ref<Tree<T>>, v: T) }?

Wariant dostaje świeże zmienne za parametry enuma, a ustala je dopiero typ oczekiwany lub argumenty. W pierwszym przypadku nic ich nie ustala (cannot infer type parameter), a jawne argumenty typu na wariancie nie są jeszcze wspierane.

3. Co zrobi kompilator z enum List { Nil, Cons(h: i32, t: List) }?

validate_owned_layouts przechodzi po polach wszystkich wariantów. Wariant Nil nie pomaga, bo rozmiar enuma zależy od największego wariantu. Ref przerywa cykl.

4. Co się stanie przy class Foo { x: i32 } i enum Foo { A } w jednym pliku?

Enumy, klasy, funkcje i stałe dzielą jedną przestrzeń nazw w DefTable. Odrzucony enum nie trafia do tabel, więc nie ma dwuznaczności. Ten błąd wykrył review: pierwsza wersja sprawdzała klasy, zanim je zarejestrowano.

5. Gdzie leży granica między tym PR-em a #52 i #53?

Pattern matching i exhaustiveness to #50 i #51. Dlatego mono nie instancjonuje generycznych enumów, a EnumConstruct w codegenie jest unreachable! za bramką.

6. Co robi E?.V(1), gdy E jest enumem?

Pierwsza wersja po cichu gubiła ?.. Poprawka z review: variant_path wymaga !safe. Podobnie lokalna zmienna o nazwie enuma przesłania ścieżkę.

7. Dlaczego wariant nie może się nazywać Some ani None?

T?, Some i None zostały w tym PR-ze bez zmian (kryterium akceptacji). Wybór między wariantami kwalifikowanymi a zmianą nazw należy do #54.
