1. Background

For beginners: what is an arena, and why plan one?

Bork does not free objects one by one. Objects live in arenas: regions of memory that are released all at once when a scope ends. That makes allocation cheap, but it raises a question for every object the program creates: which arena should it go into, and how long must that arena live?

Most objects die with the block that made them, so the block's own arena is fine. But an object that is returned, stored in something longer-lived, or handed to a function we cannot see into may outlive its block. That object needs an arena of its own, and that arena must not be torn down with the block. Getting this decision right is what keeps references from dangling.

The two decisions

For every object or enum allocation the compiler decides two things, and records them in a MemoryPlan:

DecisionValues
ClassLexical (goes into the enclosing region's arena) or Dynamic (gets an arena of its own)
Lifetime domainLexicalScope(n) (dies with region n) or Program (lives to the end of the program)

A third decision is separate: which regions actually emit an arena_push at run time. That is the codegen_push flag on each region in the report. A region that allocates nothing into its own arena does not need to push one.

Where the decisions came from, and where they should come from

Both decisions were made by walkers over the high-level tree (HIR): memory.rs for the plan, region_walk for the flags. RFC 0006 introduces a flat mid-level IR, MIR, where every allocation is an explicit Alloc statement and every reference store an explicit RefOp::Store. The RFC wants the planning to be a dataflow analysis over those statements, so that the old walkers can eventually go away.

The problem this PR starts with. The M3 shadow check was circular. The MIR builder, when it saw an object construction, asked the old plan whether to create a dynamic arena, and asked the old flags which regions to enter. So "MIR agrees with the old passes" really meant "MIR repeated what it was told". Nothing independent had been proved.

2. Intuition

Step 1: build MIR that knows nothing

The PR adds build_program_neutral. It builds MIR while ignoring the old plan and the old flags: every allocation goes into the current sink arena, and every region is entered. This MIR is deliberately naive. It is the raw material for the analysis.

Step 2: follow the objects

Take this program (it is programs/build/classes/walkthrough_point.bork):

class Point { name: String; x: i32; y: i32 }
fun sum(p: &Point): i32 { return p.x + p.y }
fun main(): i32 {
    val p = Point("a", 3, 4)
    return sum(&p) + p.name.length
}

In neutral MIR the analysis sees three facts, each a line of toy data:

_2 = alloc Point
origin of _2 = {n1}
→
_5 = copy _2
origin of _5 = {n1}
→
_6 = borrow _5
origin of _6 = {n1}
→
call sum(copy _6)
argument holds n1 ⇒ n1 is Program

Each allocation is a numbered origin. Copies, moves and borrows carry origins from one local to the next. The old pass could not see into a callee, so it assumed any record passed to a call may be kept forever. The new analysis keeps that same conservatism: n1 reaches a call, so n1 becomes Program, and therefore Dynamic (a program-lived object cannot sit in a block's arena).

Step 3: the rules that move lifetimes

Lexical, LexicalScope(n)
the default: dies with its region
→ a handle is made
Dynamic
RefCreate or a Ref stored in a field
→ it escapes
Dynamic + Program
returned, passed to a call, pushed into a Vec, assigned to an outer var

There is also propagation. If object A holds a Ref to B (an edge A→B) and A is program-lived or returned, then B must be program-lived too. The analysis repeats until nothing changes: a fixpoint.

Step 4: the push flags

A region pushes an arena when something inside it lands in that arena: an Alloc or RegisterDrop aimed at the current region, a dynamic arena made there, a string literal, or a presence guard. The flag also marks every enclosing region, because a child's arena sits on top of its parent's. Anything aimed at the result sink, the root, or the caller's arena does not count.

The proof. A new test compares the MIR-derived plan and flags with the old passes run again on all 255 lowerable programs of the corpus, in both directions and on every field: source span, class name, class, domain and the exact region number inside LexicalScope(n). They are equal. For the first time the equality is not circular.

3. The code

FileWhat changed
src/mir/plan.rs (new)derive_memory_plan(bodies, tcx): the dataflow. A Pass walks one body with one method per statement kind (alloc, assign, ref_op, ref_store, vec_store, escape_args), and an outer loop repeats until the facts stop growing. derive_push and stamp_push produce the flags.

src/mono.rsplan_instances now builds neutral MIR and takes the plan and flags from it. If MIR cannot be built (closures, move of a class object) it falls back to memory::plan and stamp_codegen_push. check_instance_regions skips MIR, since it only wants diagnostics.

A review-driven detail

The comparison test caught two missing rules while the analysis was written: arguments of strongCount/weakCount and intrinsics must count as call arguments, and a borrow or copy must carry origins. A later code review found that slices, casts and aggregates also dropped provenance. The corpus does not exercise those last cases, which is a reminder that the test is only as strong as the corpus.

4. What is not done yet

This is part 1 of #218. The goal was to delete memory.rs, codegen/regions.rs and the label-matching in region_walk. None of that is deleted, and the Definition of Done of #218 is not met. Follow-up issue #245 tracks the rest.

  • Four programs do not lower to MIR: three use move of a class object, one uses a closure. MIR sees 837 of the 841 allocations in memory_plan.txt; the other four are pinned in a test.
  • check() and the LSP still use the old plan on the pre-monomorphization HIR. The golden file keeps pre-mono class names such as Pair and region numbers; MIR exists only for concrete instances.
  • The HIR emitter still drives push/pop through RegionEmitter, so codegen/regions.rs cannot go before the HIR emitter does (#67).
  • The suite that links executables needs clang; on the author's machine 60 such tests could not run, so they did not exercise this change.
Known limit. The analysis is flow-insensitive and deliberately conservative, like the pass it ports. A "better" analysis would change the golden files, which is the thing this milestone must not do.
