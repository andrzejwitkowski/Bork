Jak Bork buduje MIR z HIR i jak to sprawdzić

Wyjaśnienie PR #236 (branch feat/66-mir-build, krok M2b z RFC 0006, zamyka #66): builder mir::build, flaga --emit-mir, goldeny i weryfikacja całego korpusu. MIR nadal nic nie konsumuje.

1. Tło

Dla początkujących: HIR, MIR i regiony (można pominąć)

HIR to drzewo programu po sprawdzeniu typów: zagnieżdżone bloki, if, pętle. MIR to ten sam program jako graf bloków połączonych skokami. Pętle, break i return stają się zwykłymi krawędziami. W Borku pamięć żyje w arenach, a region to fragment kodu, który może otworzyć własną arenę i zwolnić ją na końcu.

HIR

while c { ... }
→

MIR

header: switch c body: ... latch: reset, goto header exit: region_exit

Stan przed zmianą

Po #232 i #234 istniały układ typów oraz same typy MIR z drukarką i weryfikatorem, ale testowane ręcznie zbudowanymi ciałami. Nie było nic, co zamienia prawdziwy program na MIR.

Cel M2bZbudować MIR dla całego języka, wydrukować go, zweryfikować na całym korpusie programów i dać komendę bork build --emit-mir. Zgodność z dzisiejszym kodem LLVM ma być dowodzona danymi, nie opisem.

2. Intuicja

Regiony z raportu, nie z głowy

Czy blok ma otworzyć arenę, decyduje już dziś analiza w ArenaReport (flaga codegen_push). Builder jej nie wymyśla od nowa: idzie po HIR w tej samej kolejności co region_walk i bierze kolejne dzieci raportu. Raport nie ma identyfikatorów powiązanych z HIR, więc zgodność wynika wyłącznie z kolejności.

KonstrukcjaKolejność dzieci raportu
ifwarunek, potem region then, potem else
whilewarunek (w regionie nadrzędnym), potem region pętli
whenwartość, potem po jednym regionie na ramię
&&, ||, ?:prawa strona nie jest przetwarzana (jak w codegenie)

Jawne areny zamiast ukrytego stanu

Emiter LLVM trzyma ukryty „bieżący cel alokacji” (alloc_sink) i podmienia go tymczasowo. Builder ma to samo jako pole sink, ale każda operacja alokująca zapisuje arenę wprost. Przykład: w a = id(P(2)) wynik wywołania ma trafić do areny zmiennej a, więc ukryty argument wywołania to home(a), a argumenty są liczone w bieżącej arenie.

kod

a = id(P(2))
→

MIR

_4 = alloc P in fresh3 _5 = call id(copy _4) +current +home(_2)
Błąd znaleziony w przeglądziePierwsza wersja miała jako ukryty argument zawsze current, a argumenty liczyła w arenie przypisania. Żaden program z korpusu tego nie sprawdzał, więc goldeny były zielone. Dlatego dodano test na małym programie, który to wymusza.

Skąd wiadomo, że MIR jest dobry?

Trzy niezależne dowody: weryfikator przechodzi na 256 programach, dokładnie pięć programów odrzucanych przez bramę kończy się nazwaną „możliwością” (np. closure), a (z --features codegen) liczba wejść do regionu i resetów w MIR równa się liczbie Push i Reset w harmonogramie LLVM.

3. Kod krok po kroku

1. src/mir/build/

Podział na pliki: mod.rs (stan builderu, bloki, stos regionów), expr.rs (wyrażenia), stmt.rs (instrukcje i pętle), place.rs (tablice, Vec, kontrole granic), own.rs (obiekty, enumy, T?, when), refs.rs (przeniesienia, Ref, if val). Wartość if trafia do jednej zmiennej wynikowej przypisywanej w każdej gałęzi, bez węzłów phi.

2. Wyjścia z pętli i funkcji

break, continue i return emitują RegionExit dla każdego otwartego regionu, który opuszczają. Pętla otwiera region przed nagłówkiem, na krawędzi powrotnej robi RegionReset, a blok wyjścia zamyka region.

3. --emit-mir i testy

bork build --emit-mir [-o plik] program.bork

Działa bez feature codegen. Testy: mir_build (budowa i weryfikacja korpusu oraz lista pięciu odrzuceń), mir_golden (po jednym pliku na temat w tests/golden/mir/), mir_schedule (zgodność z harmonogramem LLVM).

Czego jeszcze nie maBrak StorageLive/Dead, etykiet debug poza deklaracjami, zabezpieczenia dzielenia MIN / -1 oraz sprawdzania przepływu inicjalizacji i przeniesień w weryfikatorze. To wszystko ma właściciela w issue #237 (część z nich blokuje #222 i #226).

4. Quiz Wynik: 0 / 0 (z 5)

1. Skąd builder wie, czy dany blok ma otworzyć arenę (RegionEnter)?

Raport nie ma identyfikatorów powiązanych z HIR; zgodność wynika wyłącznie z kolejności przetwarzania. Dlatego builder musi przetwarzać konstrukcje w dokładnie takiej kolejności jak walker.

2. Dlaczego w while region pętli jest otwierany dopiero po zbudowaniu warunku, choć w czasie działania warunek liczy się w tym regionie?

Kolejność dzieci raportu: najpierw warunek, potem region While. Budując warunek builder jeszcze nie zna tego regionu, więc wstawia wejście do bloku poprzedzającego nagłówek.

3. W a = id(P(2)) jaki jest ukryty argument „sink” wywołania i jak liczone są argumenty?

Wynik funkcji zwracającej obiekt ma trafić tam, gdzie żyje zmienna docelowa. Argumenty są liczone bez sinka przypisania (poza print), żeby tymczasowe nie lądowały w arenie celu. Ten błąd wykrył dopiero przegląd, bo korpus go nie pokrywał.

4. Co dokładnie dowodzi test mir_build, że zatrzymuje się pięć programów?

Test porównuje dokładną listę programów i nazw możliwości z oczekiwaną. Nowy nieobsługiwany program albo zmiana nazwy możliwości wywali test.

5. Które luki są zostawione i kto się nimi zajmie?

Szczególnie ochrona MIN / -1 jest ryzykowna: dziś robi to guard_int_div w emiterze LLVM i zniknęłaby po przejściu na backend z MIR, gdyby nikt jej nie przeniósł.
