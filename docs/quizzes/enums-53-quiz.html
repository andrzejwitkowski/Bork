Jak Bork kompiluje when: dopasowanie, regiony, własność

Wyjaśnienie zmian z brancha feat/match-lowering (PR #158, ticket #53): 25 plików, +986/−28 linii względem main. Strona opisuje ten PR, więc czytaj ją razem z nim.

1. Tło

Stan przed zmianą

Po #50 i #51 kompilator potrafił sprawdzić when: wzorce miały typy, a pokrycie wszystkich przypadków było zweryfikowane (Maranget). Po #52 enumy dało się zbudować w pamięci. Brakowało trzeciej części: przeczytać wartość z powrotem. Wyrażenie when dochodziło do expr.rs i kończyło się komunikatem `when` over patterns (see #53).

W HIR istniał już HirExprKind::Match { scrutinee, arms } z gotowymi ramionami (HirArm { pat, body }) i wzorcami (HirPatKind::Variant { index, fields }, Lit, Bind, Wildcard). Indeks wariantu we wzorcu to dokładnie ten tag, który #52 zapisuje w pamięci.

Cel #53Skompilować when tak, żeby: wybierało pierwsze pasujące ramię, wiązało nazwy z payloadem z poprawną własnością, nie gubiło i nie zwalniało podwójnie referencji, a liczba arena_push/pop zgadzała się z harmonogramem. Poza zakresem: optymalizacja drzewa decyzyjnego.

2. Intuicja

Ruch pierwszy: pytania zadawane po kolei

Najprostszy poprawny sposób to łańcuch testów w kolejności ramion. Wartość sprawdzana jest raz (scrutinee), potem dla każdego ramienia: „czy tag się zgadza? czy pole pasuje do literału?”. Jeśli nie, przejdź do następnego ramienia. Jeśli tak, wejdź do jego bloku. Pokrycie jest już sprawdzone, więc po ostatnim ramieniu kod jest unreachable.

scrutinee

wartość liczona raz
→

ramię 1

tag == 0 ?
→

ramię 2

tag == 1 ? pole == 7 ?
→

ostatnie

reszta: unreachable

Ruch drugi: ramię to region, jak gałąź if

Każde ramię jest regionem MatchArm z własną areną. Raport pamięci i harmonogram znały już te regiony (sema otwierała je od #50), więc brakowało tylko emitera, który w odpowiednim momencie wejdzie do regionu i z niego wyjdzie. Dlatego powstał nowy punkt zaczepienia RegionVisitor::match_expr, tak jak istniejący dla if val.

Ruch trzeci: nazwy to widoki, nie własność

Kluczowa decyzja: każde bindowanie jest widokiem na slot enuma. Ramię nigdy nie jest właścicielem payloadu, więc nie ma „przenoszenia z enuma” ani „zwalniania niepasującego payloadu”. Funkcja sprzątająca z #52 zostaje jedynym, kto zwalnia Ref-y, i robi to raz, gdy kończy się arena enuma. Nie ma ścieżki podwójnego zwolnienia.

Ruch czwarty: wyjątek, czyli Ref w payloadzie

Pole typu Ref<T> trzeba umieć dalej rozpakować przez if val. Wcześniej wiązało się jako &Ref<T>, a if val tego nie przyjmuje, więc rekurencyjnego enuma (lista, drzewo wyrażeń) nie dało się przejść. Teraz takie pole wiąże się jako kopia z licznikiem, tak jak odczyt pola Ref w klasie. Taka kopia musi zostać zwolniona, więc ramię, które ją wiąże, zawsze dostaje własną arenę (pat_binds_owned_ref).

Ruch piąty: brama odrzuca to, czego jeszcze nie ma

Wzorce Some/None (poza parą if val) oraz when po Ref albo wartości nullable są odrzucane z podpowiedzią „use if val”. Ewaluator wyrażeń i lista działają bez nich.

Czego ten PR nie robi
  • Nie buduje wspólnego drzewa decyzyjnego (ramiona testowane po kolei).
  • Nie przenosi payloadu z enuma (move na enumie dalej jest odrzucane).
  • Nie lowerowuje Some/None w when.
  • Nie zmienia znanego zachowania sprzed #53: wywołanie zwracające enum z Ref w pętli kumuluje licznik do końca funkcji, tak samo jak dla klas.

3.2 Ramię z własną areną (region_walk.rs)

+pub(crate) fn pat_binds_owned_ref(tcx: &TyCtx, pat: &HirPat) -> bool {
+    match &pat.kind {
+        HirPatKind::Bind { binding_ty, .. } => tcx.is_managed_ref(*binding_ty),
+        HirPatKind::Variant { fields, .. } => fields.iter().any(|f| pat_binds_owned_ref(tcx, f)),
+        ...
+    }

region_enter_forced(.., force_push) to region_enter z jednym dodatkiem: ramię z kopią Ref wymusza arena_push, nawet gdy jego treść nie alokuje. Bez tego kopia nie miałaby areny, w której zostanie zwolniona.

3.3 Główna pętla (src/codegen/llvm/match_emit.rs)

for arm in arms {
    let arm_bb  = context.append_basic_block(self.llvm_fn, "match.arm");
    let next_bb = context.append_basic_block(self.llvm_fn, "match.next");
    self.emit_pat_test(&arm.pat, value, next_bb)?;      // niepasujące: skok do next_bb
    self.cx.builder.build_unconditional_branch(arm_bb)?;
    self.cx.builder.position_at_end(arm_bb);

    region_enter_forced(driver, self, RegionSite::MatchArm, &arm.body, force)?;
    self.bind_pat(&arm.pat, value)?;                    // nazwy dopiero w regionie ramienia
    let arm_value = self.emit_presence_arm(driver, RegionSite::MatchArm, &arm.body, ...)?;
    ...
    self.cx.builder.position_at_end(next_bb);
}
// typeck zapewnił pokrycie, więc tu nic już nie pasuje
self.cx.builder.build_unreachable()?;

Wynik when użytego jako wartość trafia do bloku match.end przez phi (to samo co w if). Ramię zakończone return/break nie dokłada gałęzi do phi. Wartość własnościowa (np. String) jest kopiowana do areny wyniku przed wyjściem z regionu ramienia.

3.4 Test wzorca (emit_pat_test)

HirPatKind::Variant { index, fields, .. } => {
    let (record, object) = self.variant_slot(pat, *index, value)?;
    let tag = load i32 z elementu 0 slotu;
    let hit = icmp EQ tag, index;                   // to ten sam tag co zapisuje #52
    self.branch_unless(hit, fail)?;
    for (field_index, field) in fields.iter().enumerate() {
        if matches!(field.kind, Wildcard | Bind { .. }) { continue; }   // zawsze pasują
        let payload = self.load_payload(record, object, field_index, field.ty)?;
        self.emit_pat_test(field, payload, fail)?;                      // zagnieżdżone
    }
}

Literały: liczby i bool przez icmp, napisy przez istniejące emit_string_eq z text.rs. Pola leżą pod indeksem field_index + 1, bo element 0 to tag.

3.5 Bindowanie (bind_pat)

HirPatKind::Bind { name, binding_ty } => {
    let value = if self.cx.tcx.is_managed_ref(*binding_ty) { self.clone_ref(value)? } else { value };
    self.declare_local(&name.name, *binding_ty, value, None)
}

Wszystko oprócz Ref to przekazanie wartości już wczytanej ze slotu: skalar jest kopiowany, napis i tablica to deskryptor wskazujący w arenę enuma, klasa i zagnieżdżony enum to uchwyt. Ref dostaje clone_ref (licznik rośnie), a declare_local rejestruje jego zwolnienie w arenie ramienia.

4. Quiz

Wynik: 0 / 0 (z 8)

1. W jakiej kolejności Bork testuje ramiona when?

Ramiona są łańcuchem testów w kolejności źródła. Drzewo decyzyjne to optymalizacja, która jest poza zakresem #53.

2. Co jest w kodzie po teście ostatniego ramienia?

Sprawdzanie pokrycia (#51) gwarantuje, że któreś ramię pasuje. Dlatego nie trzeba generować obsługi „nic nie pasuje”.

3. Dlaczego bindowanie Rect(w, h) na wartości z nazwanej zmiennej nie przenosi pól z enuma?

Dzięki temu nie ma „niepasującego payloadu do zwolnienia” ani ścieżki podwójnego zwolnienia. Przenoszenie enumów (move) nadal jest odrzucane przez bramę.

4. Dlaczego pole Ref<T> wiąże się teraz jako kopia z licznikiem, a nie jako &Ref<T>?

Odczyt pola Ref w klasie już dawał kopię z licznikiem. Bindowanie z enuma zachowuje się tak samo, a wyniki obu ewaluatorów to potwierdzają.

5. Co powoduje, że ramię z takim bindowaniem zawsze wypycha własną arenę?

Zwykłe ramię bez alokacji nie wypycha areny (harmonogram to rozpoznaje). Kopia Ref jest własnością, więc potrzebuje areny, w której jej zwolnienie zostanie zarejestrowane.

6. Po co test codegen_arena_push_pop_counts_match_schedule dostał dwie poprawki?

Nowe próbki mają funkcję pomocniczą, więc część wywołań to push_child. Funkcja bork.drop.<Enum> kończy się ret bez arena_pop, bo działa wewnątrz sprzątania areny enuma.

7. Co zobaczy użytkownik przy when r { None => .. Some(n) => .. } na Ref?

Wzorce Some/None poza parą if val i when po Ref albo nullable nie są lowerowane. Brama zamienia „jeszcze nie” w komunikat z miejscem w kodzie, tak jak zrobiła to dla move enuma w #52.

8. Test expr_eval wypisuje ten sam licznik referencji przed i po trzech ewaluacjach. Co to dowodzi?

Wyciek zostawiłby licznik wyższy po powrocie, nadmierne zwolnienie niższy. Test porównuje licznik przed i po, tak samo jak programy z #52.
