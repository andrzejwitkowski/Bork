Jak kompilator sprawdza, czy when pokrywa wszystko

Wyjaśnienie #51 bez matematyki. Zaczynamy od tego, jak zrobiłby to człowiek z kartką, a dopiero potem pokazujemy, że kod w Borku robi dokładnie to samo, tylko sprytniej.

1. Co właściwie sprawdzamy

Masz enum i when, które go rozbiera:

enum Tri { Yes(b: bool), No }

when t {
    Yes(true) => ..
    No        => ..
}

Kompilator ma odpowiedzieć na dwa pytania:

  1. Czy jest wartość, której żadne ramię nie złapie? Jeśli tak, to pokazujemy ją w błędzie. Tutaj: Yes(false).
  2. Czy jest ramię, które nigdy się nie wykona, bo wcześniejsze ramiona łapią wszystko, co ono mogłoby złapać?

Nazwa fachowa pierwszego to „sprawdzanie kompletności” (ang. exhaustiveness). Algorytm, którego użyliśmy, pochodzi z pracy Luca Maranget'a, ale jego nazwisko nie jest ci potrzebne do zrozumienia pomysłu.

2. Sposób z kartką: wypisz wszystkie wartości

Gdy typ jest malutki, odpowiedź jest oczywista. Tri ma tylko trzy możliwe wartości, bo bool ma dwie. Wypisujemy je i sprawdzamy, które ramię je łapie:

wartośćYes(true)Nozłapana?
Yes(true)taknietak
Yes(false)nienieNIKT NIE ŁAPIE
Nonietaktak

Jest jedna dziura: Yes(false). To jest cały problem. Kłopot w tym, że ta metoda się nie skaluje: i64 ma ponad 18 trylionów wartości, a enum z kilkoma zagnieżdżonymi enumami daje ich setki. Potrzebujemy sposobu, który nie wypisuje wartości, tylko rozumuje o kształtach.

3. Sposób sprytniejszy: drzewko pytań

Zamiast wypisywać wartości, zadajemy o wartość pytania, jedno po drugim, tak jak w grze „dwadzieścia pytań”. Za każdym razem robimy to samo:

Cała idea w trzech zdaniach
  1. Zapytaj o pierwszą rzecz w wartości (np. „który to wariant?”).
  2. Dla każdej możliwej odpowiedzi zostaw tylko te ramiona, które jeszcze mogą pasować, i wyrzuć z nich to, o co już zapytaliśmy.
  3. Powtarzaj na tym, co zostało. Jeśli skończą się pytania, a nie zostało żadne ramię, to znaleźliśmy dziurę. Jeśli zostało choć jedno, ta gałąź jest pokryta.

Zróbmy to dla naszego Tri. W nawiasach pokazuję, które ramiona jeszcze „żyją” w danej gałęzi:

  • Pytanie 1: który wariant?
    • odpowiedź Yes — żyje: Yes(true). Zostaje pytanie o jego bool.
      • Pytanie 2: jaki bool?
        • odpowiedź true — żyje: ramię 1 → pokryte
        • odpowiedź false — nie żyje żadne ramię → DZIURA: Yes(false)
    • odpowiedź No — żyje: No. Nie ma już pytań. → pokryte

Gałąź false to moment, w którym „zostają zero ramion”. Ścieżka do niej (Yes, potem false) składa się na komunikat błędu: non-exhaustive `when`: missing `Tri.Yes(false)`. Kompilator nie przejrzał żadnych wartości; poszedł po drzewku i zauważył ślepą uliczkę.

4. Co robi _ i pominięte warianty

_ żyje w każdej gałęzi

Ramię z _ pasuje do dowolnej odpowiedzi, więc na każde pytanie „przeżywa” i jedzie dalej. Dodajmy je do przykładu:

when t {
    Yes(true) => ..
    _         => ..
}
  • Który wariant?
    • Yes — żyją: Yes(true) i _
      • Jaki bool?
        • true — żyją oba → pokryte
        • false — żyje _ → pokryte
    • No — żyje _ → pokryte

Brak dziur, więc kompilator jest zadowolony. Dokładnie dlatego _ „ratuje” każdy when.

Skrót, gdy wariantów jest dużo

Wyobraź sobie enum z dziesięcioma wariantami i when z ramionami tylko dla dwóch. Nie ma sensu rysować dziesięciu gałęzi. Wszystkie warianty, o których when nic nie mówi, zachowują się identycznie: łapią je wyłącznie ramiona _. Kompilator robi więc jedną gałąź „cała reszta”:

enum Shape { Circle(r: f64), Rect(w: i32, h: i32), Empty, Dot }

when s {
    Circle(r)  => ..
    Rect(w, h) => ..
}
  • Który wariant?
    • Circle → pokryte (ramię 1)
    • Rect → pokryte (ramię 2)
    • cała reszta: Empty, Dot — żyją tylko ramiona z _; nie ma żadnego → DZIURA: Shape.Empty, Shape.Dot

Komunikat wymienia brakujące warianty (do trzech, potem „and more”).

5. To samo pytanie, drugie zastosowanie

Ramię jest nieosiągalne, jeśli nie łapie niczego, czego nie złapały wcześniejsze ramiona. Sprawdzamy to tą samą metodą: bierzemy ramię i patrzymy, czy w jakiejś gałęzi, w którą ono wchodzi, nie ma żadnego wcześniejszego ramienia.

Przykład: ramię po _

when s {
    _     => ..
    Empty => ..      // to ramię?
}

Ramię 2 wchodzi tylko w gałąź Empty. Czy jakieś wcześniejsze ramię tam żyje? Tak: _ żyje w każdej gałęzi. Czyli ramię 2 nie złapie niczego nowego: nieosiągalne. W Borku to błąd unreachable pattern.

Przykład: ramię, które jednak coś łapie

when t {
    Yes(true) => ..
    Yes(_)    => ..      // to ramię?
}
  • Ramię 2 wchodzi w gałąź Yes, a potem w obie odpowiedzi na pytanie o bool:
    • true — wcześniejsze ramię 1 żyje → nic nowego
    • false — żadne wcześniejsze ramię nie żyje → ramię 2 łapie coś nowego

Wystarczy jedna gałąź z czymś nowym i ramię jest osiągalne.

6. Jak to wygląda w kodzie Borka

Kod w src/typeck/exhaustive.rs robi dokładnie powyższe. Tłumaczenie nazw:

W tym tekścieW kodzie
wzorzec bez typów (żeby algorytm był prosty do testowania)Pat: Wild albo Ctor (konstruktor z argumentami)
„zostaw ramiona, które jeszcze mogą pasować, i wyrzuć to, o co zapytaliśmy”specialize
gałąź „cała reszta”: tylko ramiona z _default_rows
„czy ramię łapie coś nowego?”useful (ramię nieosiągalne = nie useful)
szukanie dziur i budowanie ścieżki do błęduwitnesses, show
lista wszystkich wariantów typu, by wiedzieć, czy któregoś brakujeSig (Enum, Option, Bool, Infinite)

Przepływ jest taki: typeck sprawdził wzorce (#50), check_coverage zamienia je na proste Pat, odpala algorytm i zgłasza błędy. Stare when z parą Some(x) + None idzie inną ścieżką (if val) i tego sprawdzenia nie potrzebuje.

Skąd wiemy, że działa? Obok zwykłych testów jest test, który losuje 2000 zestawów ramion dla malutkiego typu i porównuje wynik algorytmu z metodą „z kartką” z sekcji 2 (wypisanie wszystkich wartości). Muszą się zgadzać za każdym razem.

7. Granice

  • Liczby i napisy. Wartości jest tyle, że żadna lista literałów ich nie wyczerpie, więc zawsze potrzebny jest _ albo nazwa. Bork nie analizuje zakresów: u8 z 256 literałami nadal chce _.
  • Nieosiągalne ramię to błąd, nie ostrzeżenie, bo kompilator nie ma jeszcze ostrzeżeń.
  • Literówka w nazwie wariantu bez danych (Emtpy) jest traktowana jak nazwa zmiennej, która łapie wszystko. Wyjdzie dopiero jako nieosiągalne ramię po niej.
  • Błąd bywa „po kolei”. Gdy brakuje wariantu na wierzchu, komunikat nie pokazuje jeszcze dziur w jego środku. Po naprawie pierwszej pojawi się następna.
