1. Background

Beginner background: how Bork manages memory (skip if you know arenas)

Arenas instead of a garbage collector

Most languages free memory object by object, either with a garbage collector or with explicit free calls. Bork does neither. It allocates objects into arenas: big regions of memory where allocation is just bumping a pointer, and where everything is released at once when the arena goes away. That makes allocation very cheap and makes freeing free, but it comes with a rule: nothing may point into an arena after that arena has been released.

In Bork every function call, and every nested { ... } block, gets its own region. When the function returns, its arena is popped and its memory becomes available for the next allocation. Whatever you allocated there is simply gone.

Handles

A value of a class or enum type is not stored inline. A variable of type Box holds a handle: roughly {arena, object-pointer}. The object itself lives in some arena, and the handle says which one. So a field n: N inside a Box is again just a handle to an N that lives somewhere else.

This indirection is what makes the problem in this PR possible. Two objects can sit in two different arenas and still point at each other.

The relevant background: how a return value escapes

If a function returns an object, that object cannot live in the callee's arena, because that arena is popped on return. Bork handles this with a hidden argument. A function that returns an owning value receives a result sink from its caller: a pointer to the caller's arena, passed in as an extra parameter (OwningReturn in call_abi.rs). When the function builds the value it is about to return, it allocates it in that arena. The popped callee arena is never involved.

Codegen has a field for this, alloc_sink. Normally it is empty and allocations go to the current region. When it is set, the next allocation goes there instead. The return statement sets it to the result sink around the returned expression, which is why return Box(N(42)) has always worked.

There was already a hoisting pass Before this PR, src/hoist.rs existed for strings. It spots var inner = <init> immediately followed by outer = move inner and annotates inner with alloc_in_binding = "outer", so that codegen builds inner directly in outer's arena and no copy is needed. The word "hoist" means exactly that: move the allocation of a value up to where its owner lives.

And there was also an escape check, src/escape.rs, which rejects programs where a String would outlive the arena holding its bytes. It had a rule for strings, and no rule at all for class and enum handles stored inside other objects.

2. Intuition

The bug

Here is the audit's reproduction, slightly trimmed:

class N { n: i32 }
class Box { n: N }

fun make(): Box {
    val n = N(42)      // lives in make()'s arena
    return Box(n)      // Box goes to the caller's arena, holding a handle to n
}

fun churn() { val x = N(12345) }

fun main(): i32 {
    val r = make()
    churn()            // reuses the bytes make() left behind
    println(r.n.n)     // prints 12345, not 42
    return 0
}

The returned Box is correct: it was built in the result sink. But the N it points at was built by an ordinary val, in the ordinary place, which is make()'s own arena. The program compiled, ran, and read freed memory. This is why the audit rated it P0: it is the one finding where an accepted program silently misbehaves.

The fix, in one sentence

If a local object is going to be stored inside the returned object, allocate it in the result sink in the first place. There is no copy and no move; the object is simply born in the right arena, next to its owner.

Why not copy the object instead? A copy would give the field a new identity. In Bork, class instances have identity: if two handles point at the same object, mutating one is visible through the other. Copying n into the owner's arena would silently break that. The audit says to keep identity, and the only way to do that is to allocate in the right place the first time.
An approach that looked like it worked, and didn't The first attempt was to teach the memory planner that a stored object handle keeps its target alive, by adding a lifetime edge. The audit's repro started printing 42. But a stress loop with 50 allocation rounds printed 49. The target was marked as a dynamic arena but was still freed at function exit; 42 had been luck. This is why every test in this PR runs a churn loop after the call: a single allocation is not enough to expose a dangling pointer.

The safety net

Hoisting only works when the compiler can prove it is safe, and that is a small, syntactic pattern. Everything else must not compile quietly. So the PR has two halves that mirror each other:

  • Hoist handles the simple, definite case and makes it work.
  • Escape rejects every other way a local object can end up inside a longer-lived one, with a message that says how to restructure.

The two must agree. The same function, collect_idents, answers "which local variables does this expression store?" for both of them, so a case cannot be hoisted by one and rejected by the other.

3. The cases, one by one

Step through them. Each shows a program, what the compiler decides, and where each object ends up.

Case 1. The basic case: a local used as a field of the return 
fun make(): Box {
    val n = N(42)
    return Box(n)
}
n is a class construct, used in return Box(n)→hoisted into the result sink

n is declared at the top level of the function and is a direct field of the final return. Hoisted. Prints 42.

Case 2. A chain: a → b → c 
fun make2(): C {
    val a = A(42)
    val b = B(a)
    return C(b)
}
return uses b→b's initializer uses a→both hoisted

The first version of the PR only looked at what the return stored directly, so b was hoisted but a was not. The result printed 49. The fix is a fixpoint loop in hoist_into_result: whenever a hoisted variable's initializer is itself a construct, its fields join the set, and we repeat until nothing changes. The order in which you declare the variables does not matter.

Case 3. A field read: local.n 
fun make(): Outer {
    val local = Box(N(42))
    return Outer(Box(local.n))
}
stored: local.n→root of the read is local→local hoisted

The stored value is not a bare variable but a read of a field of one. The pointer still lands inside local's arena, so collect_idents descends into the receiver of the field read. Without that, this printed 49.

Case 4. Through a call 
fun mk(a: A): B { return B(a) }
fun make(): C {
    val a = A(42)
    val b = mk(a)
    return C(b)
}
return uses b→b is a Call→b hoisted; a was passed to the call

Calls are hoistable initializers too. Here a is hoisted because b is hoisted and a is stored through it (the fixpoint), and the call's own result is built in the result sink it is given. I verified that this prints 42 after the churn loop; I did not trace every path inside the callee.

Case 5. Rejected: the return is inside an if 
fun make(flag: bool): Box {
    val n = N(42)
    if (flag) {
        return Box(n)      // error
    }
    return Box(N(1))
}
not the final statement of the top-level block→not hoisted→escape: compile error

Hoisting n unconditionally would make the other path pay for an allocation it does not need, and the analysis for "this val is only ever returned" gets much harder with control flow. So the pass stays simple, and escape rejects it: "n is freed before the value that stores it … build it directly in the constructor, or declare it at the top level of the function and return the value as its final statement."

Case 6. Rejected: assignment into an outer var 
var out = Box(N(1))
{
    val n = N(42)
    out = Box(n)           // error
}
// n's block is gone; out still points at it
n declared deeper than out→escape: error

This is the same dangling pointer reached through an assignment instead of a return. It printed 49 before the check existed. The rule here is slightly different: only locals declared in a deeper region than the owner dangle, so the check compares depths. A return has no owner depth; every short-lived local dangles.

Case 7. Already fine: a Vec of Refs 
var v = Vec<Ref<B>>()
while (i < 5) {
    val a: Ref<A> = A(i + 10)
    val b: Ref<B> = B(a)
    v.push(b)
}
return Bag(v)
elements are Ref<T>→Ref keeps its target alive

A Ref is reference-counted by the runtime, so it does not depend on this mechanism. Note also that Vec<B> of plain objects is rejected by the type checker today (elements must be Copy, String or Ref), so there is no way to put a bare local object into a Vec. If that ever changes, VecNew will need hoisting too.

4. Code walkthrough

The change is small in source (about 100 lines of Rust) and large in tests. It is easiest to read in the order the compiler runs: hoist decides, escape verifies, codegen obeys.

4.1 src/hoist.rs: decide what gets hoisted

annotate already ran the string-hoisting pass per function. It now also calls hoist_into_result on the function's top-level block.

fn hoist_into_result(block: &mut HirBlock) {
    // 1. The block must end in `return <construct>`.
    // 2. used = names stored in that construct (collect_idents).
    // 3. Fixpoint: if a used name is declared as a construct,
    //    add the names stored in *its* initializer; repeat.
    // 4. Every `val` in the block whose name is in `used` and whose
    //    initializer is a construct or call gets
    //    alloc_in_binding = Some(RESULT_SINK).
}

RESULT_SINK is the string "$result". It reuses the existing alloc_in_binding: Option<String> field, which normally names an outer variable whose arena to use. The $ is meant to keep it from colliding with a user variable name (I did not check the lexer's identifier rules to confirm that). A dedicated enum would be cleaner; the string was the smallest change that fit the existing field.

collect_idents is the shared helper. It walks the fields of a construct and collects the names of local variables stored there, looking through nested constructs and through the receiver of a field read.

4.2 src/escape.rs: reject everything else

  • Local::short_lived_object: a new flag, true for a val/var that holds a class or enum handle and was not hoisted. It records "this object dies with its region."
  • check_stored_objects(value, owner_depth): if value is a construct, collect the locals it stores, and report an error for any that are short-lived. With an owner_depth (an assignment), only locals declared deeper than the owner count.
  • Two call sites: the Return arm (no owner depth) and the Assign arm (owner depth is the target binding's depth).

4.3 src/codegen/llvm/emit_fn.rs: obey the annotation

if alloc_in_binding.as_deref() == Some(crate::hoist::RESULT_SINK) {
    self.alloc_sink = self.result_sink;
} else if let Some(target) = alloc_in_binding {
    // existing: look up the outer binding and use its home arena
}

Four lines. When emitting a VarDecl annotated with the result sink, point alloc_sink at the function's hidden result-sink parameter for the duration of the initializer. The existing machinery for object construction already consults alloc_sink, so nothing else needs to change.

4.4 Docs and tests

  • docs/memory-model.md: one bullet in the Hoist section describing the result-sink rule.
  • Executable fixtures in programs/build/, all with a churn loop after the call: enum, class, nested, chain, via a call, field read, method returning a Ref, a Vec of linked Refs, and a returned Option<Option<i32>>.
  • Rejection fixtures in programs/check_fail/: return in a branch, field read in a branch, assignment into an outer var.
  • The golden snapshots (memory_plan, arena_report, hir_types, hover) only gained entries for the new fixtures. No existing program changed its memory plan.

5. What this does not do

  • Only the final return of the top-level block. Other shapes are rejected rather than supported. Safe, but you may be asked to restructure.
  • Only bare locals and field reads are tracked. An object reached through some other expression is not checked by collect_idents. A method returning a bare object cannot be written today (a field read is a borrow), which is why this gap is hard to hit.
  • Conditional hoisting is not attempted. That would need real use-def analysis. The docs list it under "Still open".
  • The marker is a magic string. A dedicated enum on VarDecl would be cleaner.
  • No Vec of objects. If element types ever widen, the same dangling problem reappears for push.
The general lesson In an arena language, a pointer's validity is a property of where both ends live. You can fix a dangling pointer by moving the target, copying it, or forbidding the program. Copying breaks identity, so this PR moves the allocation when the pattern is simple enough to prove, and forbids the program when it is not.
