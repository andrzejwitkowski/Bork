1. Background

If you know what coherence means in a trait system, skip to “Where Bork stood after #56”.

Why two impls for one type are a problem

A trait says what a type can do; an impl says how. Suppose someone writes two impls of Show that both apply to Box<Circle>. When code later asks “show this box”, the compiler must choose one. If it picks differently in two places, or depending on the order of declarations, the same program means different things after an innocent reordering. Languages that care about predictability demand coherence: for any type and trait, at most one impl applies.

Overlap is about some type, not this type

The check cannot wait for a call. A generic impl such as impl<T> Show for Box<T> covers infinitely many types, and a second impl impl Show for Box<Circle> collides with it for exactly one of them. The question the compiler asks is therefore: does there exist a type that both impls would apply to? That is a question about the impl headers, not about any program that uses them.

impl AShow for Box<T>
covers Box<Circle>, Box<Square>, …
∩
impl BShow for Box<Circle>
covers Box<Circle>
=
non-emptyBox<Circle> is covered twice

Where Bork stood after #56

The previous two PRs added trait declarations and impls (#55), then bounds and a solver (#56). The solver looks up impls for a requirement like Box<Circle>: Show. With two matching impls it did the only honest thing it could: it reported an ambiguity at the use site. That worked, but the error appeared far from the real mistake, only when someone happened to call a bounded function, and the program could be full of overlapping impls that nobody used.

Key concept — unification. Bork already has unification for type inference: two types unify if replacing inference variables can make them equal. Box<?1> and Box<Circle> unify with ?1 = Circle; Box<Circle> and Box<Square> do not. Overlap detection reuses exactly this machine.

2. Intuition

The idea fits in one line: two impls overlap if their headers unify, once each impl’s own parameters are replaced by fresh variables.

Fresh variables for each impl

Each impl has its own parameter names. The T in impl<T> Show for Box<T> has nothing to do with a T in another impl. So before comparing, each impl’s parameters become separate inference variables:

impl AShow for Box<T>
T → ?1
header ABox<?1>
unify
header BBox<Circle>
no variables
impl BShow for Box<Circle>

Unifying Box<?1> with Box<Circle> succeeds with ?1 = Circle. The two impls overlap. Then the compiler rolls the bindings back, because this was only a question.

Key concept — bounds are ignored. impl<T: A> Show for Box<T> and impl<T: B> Show for Box<T> overlap even if no type implements both A and B. Deciding that would need negative reasoning (“this type will never implement B”), which the issue excludes. Being conservative can reject a program that would have been fine; it never accepts one that is ambiguous.

What happens to the error

The later impl in the file is reported, and the message names both:

error: conflicting implementations of trait `Show`:
  `Show for Box<Circle>` overlaps with the earlier impl `Show for Box<T>`;
  make the types differ or remove one

The offending impl is also dropped from the impl table. Otherwise the solver would still see two matches, and every use of that type would pile a second, confusing error on top of the first.

3. Code walkthrough

3.1 A shared header instantiation — typeck/traits.rs

The solver already built “this impl with fresh variables” inside try_impl. That logic moves into one method, ImplInfo::instantiate, which returns the self type, the trait arguments and the impl’s own bounds. The solver unifies the result with a requirement; coherence unifies two of them. ImplInfo also learns its trait_id, its program-order index and a span (the trait name in the impl header) so diagnostics can point at it.

3.2 The check — typeck/coherence.rs (new)

for each trait:
    accepted = []
    for impl in impls of that trait (source order):
        if some earlier accepted impl overlaps it:   // header unification
            report: impl overlaps with the earlier impl
        else:
            accepted.push(impl)
    table[trait] = accepted
sort reports by impl index, then emit

overlap takes a snapshot, instantiates both headers with fresh variables, unifies self types and then each pair of trait arguments, and always rolls back. One throw-away InferCtxt serves all pairs. Because the impl table is a HashMap, iteration order is arbitrary; sorting the collected diagnostics by source index makes the output identical on every run.

Edge case — three impls. With Box<T>, Box<A>, Box<A>, both later impls are compared with the accepted list, so each is reported against Box<T>. A rejected impl is never used as a reference for the next one.

3.3 Printing the headers

The message prints each impl with its own parameter names (Box<T>, not Box<T0>) and its bounds (Show for Box<T> where T: Eq). A single TraitRef::render and Predicate::render in ty/predicate.rs now build every “Trait<args>” string in the compiler, shared with the solver’s diagnostics.

3.4 The solver gets simpler — typeck/solve.rs

The “several impls apply” error is gone. With overlap rejected at declaration time, two impls can match one requirement only while some variable is still unbound, so that case now just waits (Outcome::Stalled) like any other unresolved requirement.

3.5 Tests, corpus and docs

  • src/typeck/tests/coherence.rs: unification-not-text overlaps, trait arguments, bounds ignored, disjoint impls accepted, source-order output that names both impls, no cascade into a use site.
  • A unit test in coherence.rs that checking a pair leaves no inference variables behind.
  • Programs under programs/check/traits/coherence_ok.bork and programs/check_fail/traits/overlap_*.bork. The old bound_ambiguous.bork now fails with the coherence message, which is the only change to existing golden lines.
  • docs/language.md and a note in RFC 0001 covering #55–#57.

4. What this PR deliberately does not do

No specialization. A more specific impl does not override a general one; it is simply an error. Rust has an unstable feature for that, and the issue puts it out of scope.
  • Impl self types are still classes and enums only, so blanket impls such as impl<T> Show for T cannot be written yet. The same check will handle them once they can (a bare parameter just becomes a fresh variable).
  • There is no orphan rule: Bork is a single crate, so nothing outside it can add a conflicting impl.
  • The check is conservative: bounds are not considered, so some programs that would have been unambiguous are rejected.
  • The --features codegen suite was not run locally (no LLVM 23).
