Bork od środka

Co się dzieje między „napisałem plik .bork” a „uruchamiam program”? Ta strona prowadzi przez cały kompilator, krok po kroku, na prawdziwym kodzie z repozytorium. Na końcu zobaczysz, gdzie wchodzi do tego enum (#52).

Bork to język bez śmieciarza (garbage collectora). Pamięć zarządzają areny: każdy blok { ... } dostaje kawałek pamięci, a gdy blok się kończy, cały kawałek znika naraz. Prawie każdy etap kompilatora jest po to, żeby to było bezpieczne.

src/codegen/mod.rs · build_with_options (skrót)
let mono = crate::mono::monomorphize(hir, &mut tcx, report)?;
let gate_diagnostics = gate(hir, &tcx);
// ...
llvm::emit_module(&context, hir, &tcx, report, memory_plan)
llvm::write_object_with_debug(&module, object.path(), debug)
link::link_executable(object.path(), output)

To jest tylna połowa kompilatora, trzy ruchy po kolei: dopasuj kod generyczny do konkretnych typów (monomorphize), sprawdź, czy backend to potrafi (gate), zamień na LLVM i zlinkuj z runtime.

Wcześniej działa przód: parser, typy i analiza pamięci.

Po co to wiedzieć? Kiedy AI proponuje zmianę „w kompilatorze”, najważniejsze pytanie brzmi: w którym etapie? Ta mapa mówi, gdzie szukać błędu i kto za co odpowiada.

Funkcja frontend::check robi całą pracę „zanim cokolwiek zostanie wygenerowane”. Kliknij „Dalej”, żeby przejść etapami.

Każda linia to jeden z etapów z diagramu. Dane płyną jak w rurze: wynik typecka (hir, tcx) idzie do sema, escape i memory.

Wszystkie błędy trafiają do jednej listy diagnostics. HIR istnieje tylko wtedy, gdy ta lista jest pusta.

Typy i HIR: wspólny język etapów

Każdy typ w programie ma jeden numer (TyId), a jego kształt siedzi w jednym miejscu, TyCtx. Dzięki temu porównanie dwóch typów to porównanie dwóch liczb.

src/ty/mod.rs · TyData (skrót)
pub enum TyData {
    Prim(Prim),
    String,
    Class(DefId, Vec<TyId>),
    Enum(DefId, Vec<TyId>),
    Array { elem: TyId, len: u32 },
    Ref(TyId),
    ManagedRef(TyId),
    Vec(TyId),
    Nullable(TyId),
    Param(ParamIdx),
    // ...
}

Lista wszystkich kształtów, jakie może mieć typ. Class i Enum niosą swoje argumenty (Maybe<i32> to Enum(Maybe, [i32])).

Param to parametr typu, który żyje tylko do monomorfizacji.

src/hir/mod.rs
pub struct HirProgram {
    pub classes: Vec<HirClass>,
    pub enums: Vec<HirEnum>,   // dodane w #52
    pub functions: Vec<HirFunction>,
}

HIR to „program po typach”: klasy, enumy i funkcje, każde wyrażenie ma już swój TyId.

Do #52 enumy istniały tylko w typach i wyrażeniach. Teraz mają własną definicję, bo backend musi wiedzieć, jak wygląda każdy wariant.

Aha! HIR jest granicą między „co programista napisał” a „co maszyna ma zrobić”. Wszystko po stronie HIR ma już typy, więc kolejne etapy nie zgadują.

Pamięć: areny i plan alokacji

Wyobraź sobie biurko z szufladą na każdy projekt. Wszystko, co powstaje przy projekcie, wkładasz do jego szuflady. Gdy projekt się kończy, wysypujesz całą szufladę jednym ruchem. Nie szukasz pojedynczych kartek. Tak działa arena.

src/memory.rs
pub enum ArenaClass {
    Lexical,
    Dynamic,
}
pub enum LifetimeDomain {
    Program,
    LexicalScope(usize),
}
pub struct MemoryPlan {
    pub allocations: Vec<ArenaPlan>,
}

Lexical: arena żyje tyle co blok {}. Dynamic: arena tworzona w czasie działania, bo wartość musi przeżyć blok albo jest wskazywana przez Ref.

MemoryPlan to lista decyzji: dla każdego miejsca, gdzie powstaje obiekt, w której arenie ma leżeć i jak długo.

Ważne w #52. Konstrukcja enuma trafia do tego samego planu co konstrukcja obiektu klasy (ObjectConstruct i EnumConstruct przechodzą przez tę samą gałąź w memory.rs). Wcześniej kompilator traktował enumy „zachowawczo”, bo backend ich nie umiał.

Mono i brama: zanim wejdzie LLVM

Generyk jak Maybe<T> to przepis, nie gotowe danie. Backend potrzebuje konkretów, więc monomorfizacja (src/mono.rs) robi osobną kopię dla każdej użytej kombinacji: Maybe<i32> i Maybe<String> to dwa różne typy z dwoma układami w pamięci.

src/mono.rs
pub(crate) fn enum_instance_name(tcx: &TyCtx, ty: TyId)
    -> Option<String> {
    let (def, args) = tcx.enum_args(ty)?;
    Some(mangle(tcx.class_name(def), tcx, args))
}

Nazwa instancji powstaje z nazwy enuma i argumentów: Maybe<i32>. Pod tą nazwą backend szuka układu w pamięci.

Tak samo robi się to dla klas (class_instance_name). #52 dodało wersję dla enumów.

Potem brama (codegen_gate.rs) pyta: „czy backend umie to wygenerować?”. Zamiast paniki w LLVM użytkownik dostaje czytelny błąd z lokalizacją. Do #52 brama odrzucała każdy enum. Teraz przepuszcza je, a odrzuca tylko to, czego jeszcze nie ma, np. move na enumie.

Backend i runtime: kto z kim rozmawia

Kompilator nie robi pamięci sam. Generuje kod LLVM, który w czasie działania woła bibliotekę bork_runtime (napisaną w Rust): bork_arena_alloc, bork_arena_register_drop i tym podobne. Zobacz rozmowę przy budowaniu enuma:

src/codegen/llvm/managed_ref.rs · emit_enum_construct (skrót)
let (record, size, align) =
    (layout.variants[tag as usize], layout.size, layout.align);
let object = builder.build_call(
    self.cx.arena_alloc_fn(),
    &[arena.into(), size.into(), align.into()], "enum")?;
let tag_slot = builder.build_struct_gep(record, object, 0, "enum.tag")?;
builder.build_store(tag_slot, i32_type.const_int(tag, false))?;
// pola: store_owned_field(...) dla każdego payloadu
if let Some(drop_fn) = self.cx.enum_drops.get(enum_name) {
    builder.build_call(arena_register_drop_fn(), ...)?;
}

To jest kod, który pisze kod. Kompilator buduje w LLVM instrukcje: „zaalokuj size bajtów”, „zapisz tag”, „zapisz pola”, „zarejestruj sprzątanie”.

Rozmiar bierze z największego wariantu, więc każda wartość tego enuma zajmuje tyle samo miejsca.

Dlaczego Ref nie jest kopiowany bitowo? RefHandle w runtime ma trzy pola (control, object, kind) i liczniki referencji. Kopia bitowa nie zwiększyłaby licznika, więc obiekt zniknąłby za wcześnie albo nigdy. Dlatego payload enuma przechodzi przez ten sam kod co pola klas.

Cały obraz: droga jednego enuma

Weźmy enum Shape { Empty, Rect(w: i32, h: i64) } i val s = Shape.Rect(2, 3). Zobacz, co robi z tym każdy etap.

Układ slotu dla wariantu Rect. Test enum_slot_is_sized_for_its_biggest_variant w tests/build.rs sprawdza w wygenerowanym IR, że wszystkie warianty alokują ten sam rozmiar.
