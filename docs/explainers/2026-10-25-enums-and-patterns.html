Enumy i wzorce w Borku

Przewodnik po zmianach #49 (enumy: składnia, typy, konstrukcja wariantów) i #50 (wzorce w when), razem z mapą tego, jak jest podzielony kompilator.

Spis treści
  1. Tło: jak działa kompilator Borka
  2. Intuicja: czym jest wzorzec i czemu nie wystarczy if val
  3. Kod: co dokładnie się zmieniło
  4. Co dalej: #51–#53 i metody na enumach
  5. Quiz

1. Tło

Dla początkujących: z czego składa się kompilator (można pominąć)

Kompilator to ciąg przekształceń. Każdy etap bierze strukturę zbudowaną przez poprzedni i albo ją wzbogaca, albo tłumaczy na bardziej „maszynową". Dzięki temu każdy etap odpowiada na jedno pytanie: czy to w ogóle jest poprawny tekst?, czy typy się zgadzają?, kto jest właścicielem pamięci?, jak to zamienić na instrukcje procesora?

Dwie struktury są ważne dla dalszej lektury. AST (drzewo składniowe) odzwierciedla to, co użytkownik napisał: when s { ... } to węzeł z wartością i listą ramion. HIR (high-level IR) to to samo drzewo po sprawdzeniu typów: każdy węzeł niesie już swój typ, a nazwy są rozwiązane. Etapy późniejsze, takie jak generator kodu LLVM, czytają HIR, a nie AST.

Z tego wynika praktyczna reguła, która rządzi całym tym PR-em: nowy rodzaj węzła trzeba obsłużyć w każdym etapie, który przechodzi po drzewie. Rust pomaga, bo match bez wszystkich wariantów się nie skompiluje. Stąd liczba plików w diffie.

Potok Borka

Bork ma klasy, Ref<T> (zarządzany uchwyt), generyki i arena-based zarządzanie pamięcią. Funkcja frontend::check spina część analityczną; bork build dokłada generowanie kodu. Kolory poniżej pokazują, co ruszyły #49 i #50.

Co już było: when i if val

Ref<T> może być żywy albo pusty (None). Żeby dostać się do pola, trzeba najpierw sprawdzić obecność:

when r {
    Some(n) => { n.name }
    None    => { "root" }
}

Parser traktował to jako lukier na if val n = r { ... } else { ... }. Cała reszta kompilatora zna tylko if val: typeck produkuje HirExprKind::PresenceMatch, sema otwiera regiony IfValSome i IfValNone, a codegen potrafi je wyemitować. when był więc w praktyce „dwuramienną" konstrukcją, bez wzorców.

Co dołożył #49: enumy

Enum to typ, którego wartość jest jednym z kilku wariantów, każdy z własnym ładunkiem (payload):

enum Shape { Circle(r: f64), Rect(w: i32, h: i32), Empty }

val a = Shape.Circle(1.0)
val b = Shape.Empty

#49 dodał: węzły Enum i Variant w AST; DefKind::Enum i DefKind::Variant w DefTable (z kolizjami nazw); TyData::Enum(def, args) w systemie typów, obok TyData::Class; sprawdzanie ładunków (także generycznych) i HirExprKind::EnumConstruct. Dodał też bramkę: backend jeszcze nie ma układu pamięci enuma, więc codegen_gate odrzuca każdy typ, który wspomina enum.

Luka po #49Można było enum zbudować, ale nie dało się go rozebrać. Nie istniał żaden sposób, by z Shape wyciągnąć r. To jest dokładnie luka, którą zamyka #50.

2. Intuicja

Wzorzec to opis kształtu wartości z dziurami, w które wpadają nazwy. Dopasowanie robi dwie rzeczy naraz: sprawdza, czy wartość ma ten kształt, i nazywa jej części.

val s = Shape.Rect(2, 3)
Circle(r)
kształt się nie zgadza
Rect(w, h)
pasuje: w = 2, h = 3
Empty
nie sprawdzane

Pierwsze pasujące ramię wygrywa. Wzorce zagnieżdżają się: Both(Empty, Circle(r)) dopasowuje parę, w której pierwszy element to Empty, a drugi to koło. Są też: _ (pasuje do wszystkiego, nic nie nazywa), literały (1, true, "x") oraz Some(p) i None.

Problem: kto jest właścicielem ładunku?

W języku z areną pamięci „nazwanie części" nie jest niewinne. Gdyby p w A(p) przeniosło klasę P z e, to po when zmienna e byłaby w połowie wypatroszona. #50 wybiera najprostszą bezpieczną regułę:

Tryb wiązania
  • Wartość nazwana (zmienna, pole, this) albo &T → nazwa jest pożyczką &T. Nic nie wychodzi z oryginału.
  • Wyjątek: skalary Copy (liczby, bool) wiążą się przez wartość: kopiowanie jest tanie i nie ma czego pożyczać.
  • Wartość tymczasowa (wynik wywołania) → nazwa ją przejmuje.
KodTyp nazwyDlaczego
when e { A(p) => .. }, p: P (klasa)&Pe jest zmienną, a P nie jest Copy
when e { B(n) => .. }, n: i32i32skalar Copy
when make() { A(p) => .. }Ptymczasowa wartość, nikt inny jej nie trzyma

Stare when musi działać tak samo

Kryterium akceptacji #50 mówi: wszystkie istniejące programy z when mają się nie zmienić. Najtańszy sposób, żeby to zagwarantować, to nie dotykać ich ścieżki. Parser rozpoznaje dokładnie parę Some(nazwa) + None i produkuje ten sam IfVal co dawniej. Wszystko inne trafia do nowego węzła Match.

when <wartość> { ramiona }
Some(x) + None
→ Expr::IfVal
stare regiony, stary codegen
cokolwiek innego
→ Expr::Match
nowe: wzorce, typeck, HIR

3. Kod

Krok 1: składnia (ast.rs, parser.lalrpop, ast_number.rs)

Nowe typy: Pattern (Wildcard, Binding, Literal, Variant, Some, None), MatchArm { pat, body } i Expr::Match. Reguła WhenExpr w gramatyce zbiera teraz dowolną listę ramion wzorzec => { blok }, a rozstrzygnięcie „czy to stara para" robi funkcja Expr::when już po sparsowaniu. To świadomy wybór: rozróżnianie dwóch kształtów w samej gramatyce LALR groziłoby konfliktami. ast_number.rs przydziela AstId nazwom we wzorcach, bo typeck zapisuje pod nimi typ wiązania (potrzebny np. do podpowiedzi w edytorze).

Krok 2: HIR (hir/mod.rs, number.rs, resolve.rs)

HirExprKind::Match { scrutinee, arms: Vec<HirArm> }
HirArm { pat: HirPat, body: HirBlock }
HirPat { kind, ty, span }
HirPatKind = Wildcard | Bind { name, binding_ty } | Lit(..)
           | Variant { enum_name, variant, index, fields } | Some(..) | None

Zwróć uwagę, że HirPatKind::Variant przechowuje index wariantu. Dzięki temu #51 (kompletność) i #53 (lowering) nie muszą szukać wariantu po nazwie. resolve.rs przepisuje typy w całym drzewie (np. po podstawieniu argumentów generyków), więc wzorce muszą w tym uczestniczyć.

Krok 3: typeck (typeck/expr/pat.rs, control.rs::check_match)

Sedno PR-a. check_match sprawdza wartość, ustala, czy wiązać przez pożyczkę (czy to miejsce lub &T), a potem dla każdego ramienia otwiera zakres, woła check_pat i sprawdza ciało. check_pat jest rekurencyjne i dostaje oczekiwany typ: dla zagnieżdżonych wzorców to typ pola ładunku po podstawieniu argumentów generycznych.

enum Box<T> { Full(v: T), Empty }
val b = Box.Full(3)            // Box<i32>
when b { Full(v) => { v + 1 } ... }
//        ^ pole ma typ T → po podstawieniu i32, więc v: i32

Błędy, które łapie: nieznany wariant, wariant z innego enuma, zła liczba pól, powtórzona nazwa we wzorcu, literał złego typu, wzorzec wariantu na wartości, która nie jest enumem, oraz ramiona o różnych typach, gdy when jest używane jako wartość. Gdy wzorzec jest zepsuty, jego podwzorce i tak są sprawdzane względem typu błędu: nazwy zostają zadeklarowane, więc ciało ramienia nie sypie lawiną fałszywych „nieznana zmienna".

Drobna decyzjaGoła nazwa, która pisze się jak wariant bez ładunku matchowanego enuma (Empty), jest tym wariantem. Każda inna goła nazwa jest wiązaniem. Wadą jest literówka: Emtpy po cichu staje się wiązaniem łapiącym wszystko. Dlatego #51 powinno ostrzec przed nieosiągalnymi ramionami.

4. Co dalej

  • #51 Kompletność: algorytm Maranget'a nad HirPat; zastępuje specjalny przypadek Some/None; brakujące warianty z kontrprzykładami.
  • #52 Układ enuma w pamięci: znacznik + unia ładunków, konstrukcja, drop aktywnego wariantu. Dopiero to pozwoli zdjąć bramkę.
  • #53 Lowering matchy: drzewo decyzyjne, regiony dla wiązań, przenoszenie lub pożyczanie ładunku. Tu wraca decyzja o trybie wiązania z #50.
  • Metody na enumach (styl Kotlin/Java): nie ma ich ani w #49, ani w #50. Parser enuma przyjmuje dziś tylko warianty, a check_method_call wymaga klasy. Metoda dostaje this: &Enum, więc when this { ... } działa dzięki trybowi wiązania z #50: this jest nazwą, więc ładunki wiążą się przez pożyczkę.
