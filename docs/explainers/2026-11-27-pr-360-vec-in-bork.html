Vec<T> is now an ordinary class: where it lives and how it grows

Explainer for PR #360 (issue #285) · branch feat/285-vec-in-bork · 2026-11-27

For a long time Vec was a guest in the compiler: a type with no fields, a 32-byte header the code generator knew by heart, and a dozen special statements in the middle of the IR. This PR moves it into the prelude, as src/prelude/vec.bork, written in the language it serves. The interesting part is not the move itself. It is the question that follows: where in memory does a Vec live now, and who owns which bytes? That is what this page is about.

1. Background

New to Bork's memory model? Read this first (skip if you know arenas)

Bork has no garbage collector and no free. Memory is handed out by arenas. An arena is a pool of pages (4096 bytes each). Allocating means bumping a pointer inside a page, which is very cheap. You almost never free a single object. Instead, when the region of code that owns the arena ends (a block, a loop iteration, a function), the whole arena goes at once.

Two consequences shape everything below. First, an object must never outlive its arena, so the compiler tracks which arena each value lives in and rejects code that would leave a dangling pointer. Second, an arena does not give memory back piece by piece: if you allocate a bigger buffer, the old one stays where it was until the arena dies.

arena of the block { ... } (pages of 4096 B, bump allocation)

obj B100 B

→ offset moves right on every allocation; nothing is ever moved or freed on its own
Allocations over 2048 bytes get their own system block instead of a slot in a page (docs/arena-allocation.md).

The pieces this PR builds on

  • Objects are handles. A value of a class type is a 16-byte handle {arena, object pointer}. The handle remembers which arena the object lives in. That is how a method can say arenaOf(this).
  • Buf<T> (PR #354) is a raw buffer handle {ptr, cap: i32}. It carries no arena. It is only usable inside unsafe code, and only the prelude can write unsafe. opaque class (PR #357) hides a class's fields and constructor from user code.
  • Primitives. bufAlloc, bufGrow, slotLoad, slotStore, abort and arenaOf(this) are the whole toolbox. Every index is bounds-checked and aborts on a bad one.

What Vec used to be

Before this PR a Vec value was a pointer to a 32-byte header {buf, len, cap, arena} allocated once in the owner arena, with compiler-built methods (VecOp) and a special drop function for Vec<Ref<T>>. Every new collection would have needed the same compiler code, and a user could not write impl Trait for Vec<T> because Vec was not a real class.

2. Intuition

The new design is a deliberately boring one: a Vec is a two-field class, and the elements live in a separate buffer that the class points to.

opaque class Vec<T> {
    buf: Buf<T>   // the elements: {ptr, cap}
    n: i32        // how many slots are live
}

Everything else follows from two rules. Rule one: the object is allocated in the arena of the place that declares it. Rule two: every method that needs memory (push growing the buffer) allocates in arenaOf(this), which is that same arena. So the object and its buffer always share an arena, and they die together.

arena A (the block that wrote var v = Vec::<i32>())

buffercap × 4 B
…
object.buf.ptr → the green block, in the same arena
handle (in a local){arena = A, ptr}
The handle you hold knows arena A. push reads it with arenaOf(this) to decide where a bigger buffer goes.
The one-sentence versionA Vec is a small object plus a buffer, both in the arena where the vector was declared, and growth allocates a bigger buffer in that same arena and abandons the old one until the arena ends.

3. Memory layout in detail

The object (24 bytes)

These numbers come straight from the layout golden (tests/golden/mir_layout.txt): class Vec<i32> size=24 align=8 fields=[0, 16]. The first field is a Buf, which is a pointer plus an i32 capacity (16 bytes with padding). The second field is the live count.

buf.ptroffset 0, 8 B
buf.capoffset 8, 4 B
padoffset 12
noffset 16, 4 B
padoffset 20
n is the number of live elements (len()). buf.cap is the number of slots allocated (capacity()). Always n ≤ cap.

The buffer

The buffer is cap slots of the element's size. Slots 0..n are live, slots n..cap are allocated but never read: get and set check against n, not cap, and abort otherwise.

So the old buffer stays until the arena dies. It is bounded: with doubling, all abandoned buffers together are smaller than the current one (4 + 8 + … + cap/2 < cap), so a vector wastes at most about as much memory as it uses.

4. How it grows

Growth policy is copied byte for byte from the old implementation: nothing is allocated for an empty vector, the first push allocates 4 slots, and afterwards capacity doubles. Vec::<T>(n) allocates exactly n slots up front and then doubles from n. A negative n aborts.

fun push(v: T) {
    cap = this.buf.cap()
    if (this.n == cap) {
        var next = cap * 2
        if (next == 0) { next = 4 }
        if (cap > 1073741823) { next = 2147483647 }   // clamp: cap * 2 would wrap
        this.reserveExact(next)          // bufGrow in arenaOf(this)
    }
    slotStore(&b, this.n, v)
    this.n = this.n + 1
}

The Vec object never moves, so every handle to it stays valid across growth. Only buf, inside the object, changes.
Large buffersThe arena puts blocks over 2048 bytes outside its pages, in their own system allocation. A Vec<i32> crosses that line at 513 elements (cap 1024 = 4096 B). It changes where the bytes live, not who owns them: the arena still releases the block when it ends.

Two vectors filled in one loop

A question worth asking: what if two vectors grow side by side?

val wektor  = Vec::<i32>()
val wektor2 = Vec::<i32>()
for (i in 0..10) {
    wektor.push(x)
    wektor2.push(y)
}

(In real Bork both would be var, since push mutates. Assume ten iterations and i32 elements.) Three things decide the layout.

  1. Both objects live in the same arena. Both are declared in main's block, so each 24-byte Vec object goes into that block's arena, call it A. Each Vec::<i32>() also creates a VecSeed in its own fresh dynamic arena, which stays empty and lives until exit (#358). Those seeds are not part of A.
  2. Buffers go to arenaOf(this), which is A, not the loop. The loop body has its own region that is reset after every iteration. A buffer allocated by bufGrow is placed in the vector's arena, so growth during iteration 4 does not land in the iteration's region and is not wiped when the iteration ends.
  3. Growth is interleaved. Both vectors run the same schedule (4, 8, 16), so they grow in the same iterations, one right after the other, and the arena hands out addresses in call order.

Totals in arena A, by the arithmetic above (arena page and alignment overhead not counted):

  • Objects: 2 × 24 = 48 B.
  • Live buffers: 2 × 64 = 128 B, of which 2 × 40 = 80 B hold data and 2 × 24 = 48 B are spare capacity.
  • Abandoned buffers: 2 × (16 + 32) = 96 B, unreachable but kept until A ends.
  • Total: 272 B in A. All blocks are well below the 2048-byte threshold, so they sit in A's first 4096-byte page.
What interleaving costsThe two live buffers are not adjacent and each is separated from the other by abandoned blocks. For two small vectors this is harmless. With many vectors that grow together, the abandoned blocks make up a growing share of the arena, and a long-lived arena keeps them until it ends. A vector that is created and filled in its own short-lived block avoids this, because its arena goes away with it.
One thing the loop does changeIf a for body declared a new vector (val tmp = Vec::<i32>() inside the loop), that vector's object and buffers would be in the iteration's region and would be wiped on every reset. Here both vectors are declared outside the loop, so the loop only appends to them.

5. Vectors of Ref, String and closures

For plain scalars a buffer is just bytes. The other element types own something, and that is what the buffer glue added in this PR is for.

Vec<Ref<T>>: zeroed slots and one drop per buffer

A Ref slot holds a counted reference to an object elsewhere. When the arena dies, every live slot must be released exactly once. The old code registered one drop on the 32-byte header. Now bufAlloc does this for a buffer of Refs:

1
Allocate the slots and zero them: an all-zero handle is None, which releases nothing.
2
Allocate a 16-byte header {ptr, cap} in the same arena and register one drop, bork_buf_drop_refs, on it.
3
When the arena ends, the drop walks all cap slots and calls bork_ref_drop on each. Zero slots are no-ops.

When arena A dies both drops run: the old one finds only None, the new one releases four references. Each exactly once.

pop on a Vec<Ref> moves the handle out of its slot (slotTake leaves None behind), and clear releases live slots with slotDrop. A push over a live slot goes through bork_ref_store_take, which releases the old value first.

String and closure elements

A String is a {ptr, len} descriptor. Storing one copies the bytes into the vector's arena, so the string survives the block that created it. A closure element has its captured environment copied into the vector's arena for the same reason, and an owned Ref capture is cloned and registered for release there.

6. Moving a vector between arenas

A Buf holds a raw pointer into one arena, so you cannot simply copy a Vec handle to an outer arena: the buffer would be left behind in an arena that is about to die. Instead the PR copies the contents.

7. Code walkthrough

A. Buf learns about its elements (runtime and codegen)

  • codegen/llvm/buf.rs: buf_alloc zeroes Ref buffers and registers bork_buf_drop_refs; buf_grow zeroes the old slots; buf_store_in stores a Ref through bork_ref_store_take or copies a String into the arena. Buffers and headers are labelled Buf<T> / BufHeader for the debug registry.
  • bork_runtime/src/refs.rs: bork_buf_drop_refs replaces bork_vec_drop_refs. A test grows a buffer, overwrites a slot, takes a handle out and checks the exact strong and weak counts after the arena ends.
  • New primitives: slotCopy, slotDrop, slotTake, refNone, and the view ops used by &v[i].

B. Vec in the prelude

  • src/prelude/vec.bork: Vec, VecSeed, vecNew, vecWithCapacity, and the methods push pop get set len capacity clear plus the private helpers reserveExact reserveAtLeast assignFrom popRef (user calls to them are rejected).
  • src/prelude.rs: the Vec chunk needs Buf; chunk dependencies are now resolved transitively, both for loading and for blocking when a user defines their own Buf.

C. The compiler learns that Vec is a class

  • Typeck: v[i] and v[i] = x become get/set; Vec::<T>() calls vecNew; the old rules are kept (element set, val receiver, closure push, not nullable, impl Trait for Vec rejected); a mutating method inside a closure makes it FnMut; pop of a Ref element becomes popRef.
  • MIR: &v[i] lowers to a slot-view intrinsic whose receiver operand names the vector, so mir::borrows locks the vector while the view lives; vector factories allocate where declared; VecOp is gone.
  • Memory plan: Vec.push/set mark their argument as outliving the call, as VecOp::Push used to.
  • Deleted: VecOp, VecNew, AllocKind::Vec, DropGlue::Vec, LangItem::Vec, codegen/llvm/vec/, the 32-byte header.

D. Tests

The existing corpus is the contract: every programs/build/vec program (exit code, stdout, plain and -g builds) and every programs/check_fail/vec diagnostic had to pass on the Bork Vec before the old one was deleted. New programs cover promote and move, returning from a function and from a loop, capacity growth, abort cases, Ref pop, and releasing the tail on promote.

8. Known limits

  • Every Vec::<T>() allocates a throw-away VecSeed arena that lives until the program exits (#358).
  • make()[0] on a call result is rejected, as is a local named vecNew shadowing the factory (#361). Element-view locking is not field-sensitive (#362).
  • Promote, move and closure capture copy element by element (not memcpy), and a copy made by return/closure capture has cap = len.
  • impl Trait for Vec<T> is still rejected on purpose; allowing it is #359.
