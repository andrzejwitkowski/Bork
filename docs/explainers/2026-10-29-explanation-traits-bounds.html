1. Background

If you know what a bound and a trait solver are, skip to “Where Bork stood after #55”.

What is a bound?

A generic function such as fun show_twice<T>(t: &T) works for every type, which means its body can do almost nothing with t. A bound narrows the promise: fun show_twice<T: Show>(t: &T) says “only types that implement Show”. In return the body may rely on that. The caller carries the burden: before the call is accepted, someone has to check that the type really implements the trait.

What does a solver do?

That “someone” is a trait solver. It is given a requirement such as Circle: Show and answers one of three things: yes (an impl exists), no (none does), or not yet (the type is not known so far). Rust’s solver is large; Bork’s, per RFC 0001, is deliberately small: no negative reasoning, no specialization, a depth limit.

Where Bork stood after #55

The previous PR taught the compiler to read traits and impls and to check that an impl matches its trait. It built an impl table and then threw it away: nothing consulted it. A type parameter was just a name (TypeParam { name }), and a diagnostic even said “a type parameter has no bounds yet”. Inference, from earlier phases, deliberately knew nothing about traits.

Key concept — inference variables. While checking need(make()), the argument’s type is not known at the moment of the call. Bork gives it a placeholder, an inference variable, to be filled in later by unification. A requirement on a placeholder cannot be judged yet; this is why the solver needs the answer “not yet”.

2. Intuition

The core idea fits in one sentence: a bound on a generic function is a list of requirements, and each call turns that list into obligations that the solver must discharge before the function ends.

The life of one obligation

Take this program (the toy data used throughout):

trait Show { fun show(): String }
class Circle { r: f64 }
class Square { s: f64 }
class Box<T> { v: T }
impl Show for Circle { ... }
impl<T: Show> Show for Box<T> { ... }

fun need<T: Show>(t: &T) { }

The signature of need now carries one predicate: Param(0): Show. At a call, the type parameter is replaced by the real (or placeholder) type, and the predicate becomes an obligation:

CallObligationOutcome
need(&Circle(1.0))Circle: Showdirect impl → solved
need(&Box(Circle(2.0)))Box<Circle>: Showimpl for Box<T> matches with T = Circle → solved, but it brings a nested obligation Circle: Show → solved
need(&Box(Square(1.0)))Box<Square>: Shownested Square: Show has no impl → error
need(&5)i32: Showonly classes and enums implement traits yet → error
Box<Square>: Show
→ impl<T: Show> for Box<T>, T=Square →
Square: Show (depth 1)
→ no impl →
error
“the trait bound Square: Show is not satisfied; it is implemented for: Circle, Box<T>”

Three more cases the solver must get right

  • Inside a generic body. In fun pass<T: Show>(t: &T) { need(&t) } the requirement is T: Show, and T is an opaque parameter, not a class. It is satisfied only by the function’s own bounds (its “param-env”). Without : Show on pass, the same call is an error.
  • Not yet. In val c: Circle = make(); need(&c) the type is known by the time of the call. In val x = make(); need(&x) it never becomes known: the obligation waits, and at the end of the function it is reported as “cannot infer”.
  • Too deep. A value of type Box<Box<…Circle>> nested forty times needs forty nested obligations. The solver stops at depth 32 with an overflow error instead of looping or using unbounded memory.
Key concept — why the list lives in InferCtxt but the solving does not. The obligation list sits next to the inference variables so that a snapshot (a point to roll back to when a guess fails) restores both together. But picking impls needs the impl table, which is a type-checker concern, so the logic lives in typeck/solve.rs. Unification itself stays free of traits, as the issue asks.

3. Code walkthrough

3.1 Syntax — parser.lalrpop, ast.rs

TypeParam grows a bounds: Vec<TraitRef>. The grammar accepts T: A + B<i32> in declaration position, and a where clause on functions and impls. The parser merges the where predicates into the parameters’ own bound lists (ast::merge_where), so everything downstream sees one list per parameter. where becomes a reserved word. Class, enum and trait parameters parse bounds too, but generics::validate then rejects them with one message, because nothing checks them at construction yet.

3.2 Predicates — ty/predicate.rs, ty/sig.rs

pub struct TraitRef<T>  { trait_id: DefId, args: Vec<T> }   // args exclude Self
pub struct Predicate<T>  { self_ty: T, trait_ref: TraitRef<T> }  // "self_ty: Trait<args>"

FnSig gets predicates. Because generics are positional (Param(i)), a predicate is substituted at a call with the very same subst that substitutes parameter types. typeck/traits.rs::lower_bounds turns written bounds into predicates (unknown trait, wrong argument count and duplicate bounds are diagnosed); collect_fun_sigs, collect_method_sigs and build_impls call it. An ImplInfo now also keeps the impl’s own predicates.

3.3 The obligation list — infer/obligation.rs, infer/mod.rs

Obligation { predicate, span, depth, origin } and a list in InferCtxt. Snapshot records the list length and rollback_to truncates it, so a probe that registers obligations and then fails leaves no trace. There is a unit test for exactly that.

3.4 The solver — typeck/solve.rs

  1. register (called from subst_sig, so both function calls and method calls share it) substitutes the callee’s predicates with the call’s type arguments, queues them, and runs select_where_possible.
  2. solve_one resolves the types and branches on the head: an inference variable → stall; a Param → look in the function’s bounds (solve_from_bounds); a class or enum → solve_from_impls; anything else → error. Already-erroneous types are dropped silently, so one mistake is one error.
  3. solve_from_impls probes every impl of the trait inside a snapshot (try_impl: fresh variables for the impl’s parameters, unify header). Zero matches is an error listing the impls; one match is committed and its bounds become nested obligations at depth + 1; several matches is an ambiguity error, or a stall if a variable is still open.
  4. report_unsolved runs at the end of check_function, after literal defaulting and report_uninferred; whatever is still waiting is reported.

3.5 Tests, corpus and docs

  • src/typeck/tests/bounds.rs: lowering, satisfied and unsatisfied calls, nested impl bounds, in-body bounds, waiting, literal defaulting, ambiguity, depth limit, no-cascade, declaration errors, methods.
  • Programs under programs/check/traits/bound* and programs/check_fail/traits/bound*; five golden snapshots re-blessed with additions only.
  • Follow-ups from review: an impl method cannot add bounds its trait method lacks; TyCtx::display_with prints an impl’s own parameter names without mutating shared state.

4. What this PR deliberately does not do

No method calls through bounds. Inside fun f<T: Show>(t: &T) you still cannot write t.show(). Bounds only decide whether other calls are allowed. Method resolution and the static dispatch that makes it run come in #58.
  • A parameter that appears only in a bound (fun g<T: Show>()) is accepted by the type checker but rejected by monomorphization, which cannot recover T from the signature yet.
  • Primitives and Vec implement no traits (impl Self is still class or enum only).
  • Overlapping impls are an ambiguity error at the use site until #57 rejects them at the declaration.
  • The --features codegen suite was not run locally (no LLVM 23).
