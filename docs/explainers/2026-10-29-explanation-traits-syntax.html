1. Background

If you already know what traits are and how a compiler front end is laid out, skip to the second half of this section, “How Bork checks a program today”.

What is a trait?

A trait is a named list of method signatures. It says “anything that wants to be a Shape must be able to compute an area”, without saying how. A separate impl block then declares that a concrete type, say Circle, satisfies the trait by supplying the bodies. The same idea is called an interface in Java or Go, a protocol in Swift, and a trait in Rust, which is the closest relative of what Bork is building.

trait Shapefun area(): f64
⇠ promises
impl Shape for Circlefun area(): f64 { … }
⇠ provided by
class Circler: f64

Bork’s design (RFC 0001) chooses monomorphization: generic code is copied once per concrete type, so a call through a trait becomes an ordinary direct call. No vtables, no inheritance. That decision shapes this whole phase, but it only matters from ticket #58 on.

How Bork checks a program today

The front end is a pipeline. Source text is parsed (by a LALRPOP grammar in src/parser.lalrpop) into an AST (src/ast.rs). A DefTable (src/defs.rs) then gives every declaration a stable DefId and records name clashes. Finally typeck::check_with_members lowers written types to interned TyIds, collects function signatures, and checks bodies.

Sourcetrait Shape {…}
→
Parser → ASTProgram { classes, enums, functions, traits, impls }
→
DefTableDefId per declaration, clash list
→
Typecklower types, collect sigs, check bodies
Key concept — generics are positional. A type parameter is not stored by name inside a type; it is Param(i), an index into a flat list: the owner’s parameters first, then the item’s own. generics::scope builds that numbering. Anything that wants parameters, such as Self, has to fit into this numbering.

Before this PR the language had classes with methods inside them and nothing else. docs/language.md even listed interfaces as unsupported, and the grammar had no trait or impl tokens.

2. Intuition

The essential job of this PR is small to state: when the programmer writes an impl, check that it keeps the trait’s promise. Take a toy program.

trait Shape {
    fun area(): f64
    fun scaled(k: f64): f64
}
class Circle { r: f64 }
impl Shape for Circle {
    fun area(): f64 { return r * r }
}

The checker holds the trait’s method list in one hand and the impl’s in the other, and compares them like a checklist:

Trait says area() → f64
scaled(k: f64) → f64
Impl provides area() → f64 ✔
scaled … ✘ missing

The result is one error at the impl: not all trait items implemented, missing: `scaled`. The same comparison produces five other errors, shown here with the toy data that triggers each one:

Impl containsDiagnostic
fun perimeter()method perimeter is not a member of trait Shape
fun scaled()has 0 parameters but trait Shape declares 1
fun scaled(k: i32)parameter k of scaled has type i32 but … declares f64
fun area(): i32area returns i32 but … declares f64
area twiceduplicate method area

The one subtle part: comparing types across generics

A trait signature can mention Self and the trait’s own parameters; an impl states them concretely. For trait Conv<U> { fun conv(u: U): U } and impl<T> Conv<i32> for Box<T>, the trait signature is stored with Self as Param(0) and U as Param(1). To compare, the checker substitutes real types for those slots, then compares the result with what the impl wrote.

Trait signatureconv(u: Param(1))
→ subst [Self=Box<T>, U=i32] →
Expectedconv(u: i32)
=?
Impl wroteconv(u: i32) ✔
Key concept — Self in an impl. Inside an impl, Self is simply rewritten to the impl’s type at the AST level (Type::with_self) before lowering. So fun dup(other: Self): Self in impl Dup for C is checked as if the author had written C.

3. Code walkthrough

3.1 Grammar and AST — parser.lalrpop, ast.rs

Two new keywords and two new item kinds. for already existed as a keyword, so impl Shape for Circle reuses it. Trait bodies list signatures only (no block, so a method body in a trait is a parse error). Bodies of traits and impls copy the newline-separated pattern of ClassBody.

pub struct Trait     { name, generics, methods: Vec<TraitMethod> }
pub struct TraitMethod { name, generics, params, return_type }       // no body
pub struct Impl      { generics, trait_name, trait_args, self_ty, self_span, methods: Vec<Function> }

Program gains traits and impls. ast_number.rs assigns node ids to the new names so the numbering test (every id dense and unique) still holds. A consequence: trait and impl are now reserved words.

3.2 Definitions — defs.rs

Four new DefKinds: Trait, TraitMethod, Impl, ImplMethod. add_traits and add_impls run in DefTable::build, and keep the existing convention of program-order parallel vectors (trait_ids, impl_method_ids…) so typeck can map AST index → DefId. A trait that shares a name with a class, enum, primitive, function or earlier trait gets a TraitConflict clash and keeps its methods out of the lookup table, so one mistake yields one error.

3.3 The checking pass — typeck/traits.rs (new)

  1. build_traits lowers each trait’s methods. The scope is [Self, trait params…, method params…], so Self is Param(0).
  2. build_impls resolves the trait name, checks the trait-argument count, lowers the self type (only classes and enums are accepted), and builds an ImplInfo in an ImplTable keyed by trait.
  3. check_impl / check_method perform the checklist comparison from the Intuition section, substituting [self_ty, trait_args…, method params…] into the trait’s stored types.

It is wired into check_with_members after the enums are built and before function signatures are collected, so it cannot disturb how existing classes are processed. generics::validate also learns to check type-parameter lists of traits and impls.

3.4 Tests, corpus and docs

  • tests/parser.rs: parse shapes and two rejection cases.
  • src/typeck/tests/traits.rs: clean impls, each impl-item error, header errors, Self, DefId kinds.

4. What this PR deliberately does not do

Impl bodies are parsed but not type-checked. The existing function checker assumes a class owner with the class’s own type parameters, which does not fit impl<T> … for Box<T>. Since nothing can call an impl until #58, a body that returns the wrong type passes for now.
  • No bounds, no solver, no method calls through traits (#56, #58).
  • The impl table is built but nothing reads it yet (hence one #[allow(dead_code)] with a shortcut: note).
  • Only classes and enums can be the self type of an impl.
  • The --features codegen suite was not run in the author’s environment (no LLVM 23).
