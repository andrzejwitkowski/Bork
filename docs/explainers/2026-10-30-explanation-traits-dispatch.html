1. Background

If you know what static dispatch and monomorphization are, skip to “Where Bork stood after #57”.

Two ways to run “the right code”

Given x.show(), where x might be a Circle or a Square, a compiler has to decide which show runs. There are two classic answers. With dynamic dispatch the decision waits until the program runs: each value carries a pointer to a table of functions (a vtable) and the call jumps through it. With static dispatch the compiler decides while compiling and writes an ordinary direct call. Bork’s RFC 0001 chooses the second, and the issue says it plainly: “no vtables”.

Monomorphization in one paragraph

Bork compiles generic code by monomorphization: a generic function fun say<T>(t: &T) is copied once per concrete type it is used with, so say<Circle> and say<Square> are two real functions with no type parameters left. That is what makes static dispatch possible: by the time the copy for Circle exists, the compiler knows that T = Circle.

Where Bork stood after #57

The first three tickets built the declarations (#55), the bounds and solver (#56), and the rule that two impls never overlap (#57). Together they say whether a type implements a trait. They did not yet let anyone use that. Three things were missing:

  • t.show() on a T: Show failed with “only named functions can be called”, because a type parameter has no class to look methods up in.
  • A class with only an impl method said “class has no method”.
  • Impl bodies were never type-checked and never emitted. The compiler compared an impl’s signatures with its trait and then ignored the code inside.
Key concept — a method call is just a call. In the HIR (the typed intermediate form), c.area() is already an ordinary function call to a function named Circle.area with the receiver as the first argument. There is no separate “method call” node, so teaching the compiler a new kind of method means giving it a new kind of function name, not a new kind of expression.

2. Intuition

The change has two halves that meet in the middle. Type checking turns x.m() into a call of an abstract name, Show.show. Monomorphization, which later knows the concrete type, replaces that name with the real function.

Half one: record the intent

For fun say<T: Show>(t: &T) { t.show() }, the checker cannot know which show will run, but it knows two things: T has the bound Show, and Show declares show. So it emits a call to Show.show and registers the obligation T: Show with the solver from #56.

Half two: pick the code

When say is specialised for Circle, the call’s type becomes concrete, (&Circle) → String. Monomorphization matches that against the trait’s signature, learns Self = Circle, finds the one impl that fits, and rewrites the callee:

Type checksay<T> calls Show.show(t)
→ specialise T=Circle →
MonoSelf = Circle
which impl? impl Show for Circle
→
Resultsay<Circle> calls Show@0.show

Note that coherence (#57) is what makes this safe. Because no two impls overlap, “the one impl that fits” always exists or does not; it is never a choice between two.

Lookup order

The checker tries the places in a fixed order, and the first hit wins:

ReceiverLooked up inExample
class or enum with an inherent method mthe class itself (always wins)Circle.show defined in class Circle
type parameter Tthe function’s own boundsT: Show ⇒ Show.show
class or enum without an inherent mimpls whose header unifies with the receiverimpl Show for Box<T>
nothing founderror: lists the bounds, or “class has no method”type parameter T has no method nope; its bounds are: Show

If two bounds both declare m, the call is rejected as ambiguous and both traits are named.

Key concept — instances get unique names. Impl methods become real functions named Trait@<impl index>.<method>. The index matters: impl Show for Box<i32> and impl Show for Box<String> are different impls with the same method name. The @ cannot occur in an identifier, so these names can never clash with anything a user wrote.

A worked example

trait Show { fun show(): String }
class Circle { r: f64 }
class Box<T> { v: T }
impl Show for Circle { fun show(): String { return "circle" } }
impl<T: Show> Show for Box<T> { fun show(): String { return v.show() } }

fun twice<T: Show>(t: &T): String { return t.show() }
fun main() { val b = Box(Circle(1.0));  twice(&b) }
Instance createdWhat it calls
maintwice<Box<Circle>>
twice<Box<Circle>>Show@1.show<Circle> (the Box<T> impl with T = Circle)
Show@1.show<Circle>Show@0.show (v.show(), with v: Circle)

Every arrow in that chain is a direct call. Nothing looks anything up while the program runs.

3. Code walkthrough

3.1 Type-checking impl bodies — typeck/traits.rs, typeck/mod.rs

check_method, which already compared each impl method with the trait, now also returns the method’s lowered signature (this: &Self first). It is stored in ImplInfo.sigs, so the types are lowered exactly once and a mistake is reported exactly once. check_function’s owner, previously “a class or nothing”, becomes an Owner enum: Class or Impl. After the class methods, check_with_members checks each impl method in source order; because the impl table is a HashMap, it sorts by impl index first so the output is deterministic.

Inside an impl, self_class is set only when Self is a class. That is why bare field names work (r * r) in a class impl, while an enum impl still gets this but no implicit fields.

3.2 Finding the method — typeck/expr/method.rs

check_method_call keeps its old path when the class has an inherent method. Otherwise it calls check_trait_method_call, which:

  1. collects candidates with trait_candidates: bounds for a type parameter, applicable impls (via the shared solve::impl_applies) for a class or enum;
  2. requires exactly one, else reports ambiguity or the list of bounds;
  3. builds the signature by substituting [Self, trait arguments, fresh variables for the method’s own parameters] into the trait’s stored signature, with &Self prepended;
  4. registers Self: Trait<args> with the solver, which fixes the trait arguments from the unique impl or waits;
  5. finishes the call as Trait.method and records a MemberRef::Method for sema and the language server.

bounds_hint is also made honest: a type parameter that has bounds no longer claims to have none.

3.3 Carrying signatures to monomorphization — hir/mod.rs, mono.rs

HirProgram gains traits and impls: signatures only, over the generic parameters. In mono.rs, retarget_expr already rewrote calls to generic functions. When a callee name is not a function but looks like Trait.method, resolve_trait_call takes over:

  • it binds the trait method’s signature (Self, trait arguments, method parameters) against the call’s now-concrete type, reusing the same bind that functions use;
  • it finds the one impl whose self type and trait arguments bind against those values;
  • it requests an instance of that impl’s method with the impl’s arguments followed by the method’s own.

The shared part of infer_type_args was lifted into bind_signature so functions and trait methods use one matcher. Codegen is untouched, because by now the callee is a plain name of a plain function.

3.4 Sema — sema/analyze.rs

Sema works on the AST and must produce one analysis root per HIR function, in the same order. Impl methods are appended after class methods, with this typed as the impl’s self type. The trait’s declaration also registers borrow modes under Trait.method, so a call through a trait still knows which arguments are borrowed. Without this, escape analysis would treat such a call as an unknown function and quietly lose information.

3.5 Tests, corpus and docs

  • typeck/tests/dispatch.rs (bounds, impls, shadowing, ambiguity, impl-body errors, fields in impls, trait arguments, method hints) and mono tests asserting instance names and that no Show.* callee survives.
  • Six programs in programs/build/traits/ that compile and run natively with expected output; they run only with the codegen feature, so CI’s LLVM job is what exercises them.
  • Goldens re-blessed; docs/language.md and an RFC 0001 note updated; the dead_code shortcuts left by #55 and #56 are gone.

4. What this PR deliberately does not do

Parameters that no type determines. If a trait argument or an impl parameter appears nowhere in the call’s types, monomorphization cannot recover it and reports the same “not determined” error as for a bound-only type parameter.
  • No default method bodies, no Trait.method(x) call syntax, no trait objects.
  • Impl self types are still classes and enums only.
  • A bound gives a type parameter trait methods only; operators and field access on T still need more than a bound.
  • Associated types arrive in #59.
