1. Tło

Dla początkujących: czym są traity i typy asocjowane (można pominąć)

Trait to obietnica: „każdy typ, który mnie implementuje, ma te metody". Funkcja generyczna fun say<T: Show>(t: &T) przyjmuje dowolny typ T, o którym wiadomo tylko tyle, że implementuje Show. Kompilator nie zna T, więc w ciele funkcji wolno użyć wyłącznie tego, co obiecuje trait.

Czasem obietnica musi dotyczyć też typu. Kontener ma metodę get(), ale co ona zwraca? Dla kontenera liczb i32, dla kontenera napisów String. Trait mówi więc: „każdy implementujący wybiera sobie typ Item". To właśnie typ asocjowany.

Co Bork miał przed tą zmianą

Po zadaniach #55–#58 Bork umie deklarować traity i implementacje, sprawdzać ograniczenia (T: Show), odrzucać nakładające się implementacje i kompilować wywołanie x.show() do bezpośredniego wywołania metody konkretnej klasy, bez vtable. Brakowało jednak sposobu, żeby sygnatura metody traitu powiedziała „zwracam to, co wybierze implementacja".

Monomorfizacja Funkcja generyczna jest kompilowana osobno dla każdego konkretnego typu, z którym ją wywołano: first<IntBox>, first<Named>. W Borku robi to src/mono.rs. Po niej w programie nie zostaje żaden parametr typu, więc generator kodu widzi wyłącznie typy konkretne.

Co jest ważne dla tej zmiany

  • Typy są internowane (TyId): równe typy mają równe identyfikatory, więc porównanie to porównanie liczb.
  • Ograniczenia z fun f<T: Container> trafiają do param_env funkcji; to jedyne, co o T wiadomo w jej ciele.
  • Solver (typeck/solve.rs) rozwiązuje zobowiązania w pętli. Jeśli typ jest jeszcze zmienną wnioskowania, zobowiązanie czeka.

2. Intuicja

Nowy rodzaj typu to projekcja: „typ Item, który wybrał X w traicie Container". Zapisujemy ją T::Item. Projekcja jest wyrażeniem, które trzeba obliczyć, kiedy wiadomo, czym jest X.

trait Container {
    type Item
    fun get(): Self::Item
}
impl Container for IntBox { type Item = i32;    fun get(): i32    { ... } }
impl Container for Named  { type Item = String; fun get(): String { ... } }
fun first<T: Container>(c: &T): T::Item { return c.get() }

Dlaczego parametr zostaje nieprzezroczysty W ciele first<T> nie wiemy, czym jest T. Wiemy tylko, że c.get() zwraca T::Item, a sygnatura obiecuje T::Item. Te dwa typy są tym samym internowanym typem, więc funkcja się sprawdza bez żadnej wiedzy o implementacji. Dopiero monomorfizacja podstawia konkretne T i oblicza wynik.

Wiązania równościowe

Czasem funkcja chce wiedzieć, że Item to konkretny typ. T: Container<Item = i32> dodaje do ograniczeń równość T::Item == i32. W ciele funkcji projekcja normalizuje się wtedy do i32, a każde wywołanie sprawdza, czy argument tę równość spełnia.

Wywołanie total(&x)Wynik
x: IntBox (Item = i32)poprawne
x: Named (Item = String)błąd: expected the associated type to be `i32`, but it is `String`

Pułapka: dwa traity z tym samym Item

Pierwsza wersja projekcji trzymała tylko (baza, nazwa). Jeśli Foo implementuje Container (Item = i32) i Other (Item = String), to po podstawieniu T := Foo zostawało Foo::Item i nie było wiadomo, o który trait chodzi. Dlatego projekcja niesie też nazwę traitu, ustaloną z ograniczeń funkcji.

Zapisane w kodzie

T::Item — trait jeszcze nie znany (None)

Po „kwalifikacji"

jedyne ograniczenie T: Container deklaruje Item → Projection(T, Container, Item). Zero takich — błąd. Dwa — błąd niejednoznaczności.

3. Kod

1. Składnia i AST

  • src/parser.lalrpop: słowo kluczowe type (zastrzeżone), type Item w traicie, type Item = X w implu, typ T::Item, argumenty traitu z wiązaniami <A, Item = X>.
  • src/ast.rs: Trait.assoc_types, Impl.assoc_types, TraitRef.bindings, Type::Assoc.
  • src/ast_number.rs: nowe nazwy dostają numery węzłów (test korpusowy pilnuje, żeby żaden nie został bez numeru).

2. Reprezentacja typu

  • src/ty/mod.rs: TyData::Projection(baza, Option<trait>, nazwa) i TyCtx::projection.
  • src/ty/fold.rs: children() i super_fold znają projekcję. Gałąź _ => vec![] sprawiłaby, że kompilator nie ostrzegłby o pominięciu — dlatego dodane jawnie. Nowe subst_with podmienia wskazane typy.
  • src/ty/predicate.rs, sig.rs: ProjectionPredicate i pole proj_predicates w FnSig.

3. Tabela definicji i sprawdzanie implementacji

  • src/defs.rs: rejestr nazw typów asocjowanych.
  • src/typeck/traits.rs: lower_assoc zgłasza brakujące, nadmiarowe i zduplikowane typy oraz cykle (type Item = Self::Item); qualify_sig nadaje projekcjom trait; lower_bounds zwraca teraz też wiązania równościowe i odrzuca zduplikowane.
  • Impl z wiązaniem równościowym na własnych parametrach jest odrzucany (świadomy skrót).

4. Normalizacja w typeck

  • src/typeck/solve.rs: normalize zbiera „liście" projekcji (te bez zagnieżdżonej projekcji w bazie) i dla każdego pyta project, które zwraca Done, Rigid, Stalled lub Failed. Stalled tworzy zmienną i wpis „pending", ponawiany w select_where_possible.
  • project_from_impls czyta wartość impla w snapshocie i go cofa, żeby nie zawężać zmiennych bazy.
  • Punkty wejścia: subst_sig (expr/call.rs), początek check_function (typeck/mod.rs) i Env::lower.

5. Monomorfizacja

  • src/hir/mod.rs: HirImpl.assoc niesie type Item = X do mono.
  • src/mono.rs: normalize_projections po podstawieniu typów wybiera impl tego traitu, którego nagłówek pasuje do bazy, i podstawia parametry impla. no_params_left sprawdza też brak projekcji.
Znane ograniczenia Pisz Self::Item (samo Item nie jest aliasem). Brak <T as Trait>::Item, ograniczeń na typach asocjowanych, domyślnych wartości i GAT. C::Item? się nie parsuje. Normalizator istnieje w dwóch kopiach (typeck i mono), bo pierwszy działa na kontekście wnioskowania, drugi na samych typach.
