Who lets go of a reference when the memory goes away?

An explanation of PR #210 (issue #62, "generic drop glue") in the Bork compiler.

1. Background 2. Intuition 3. The code 4. Quiz

1. Background

If you already know how Bork's arenas and Ref counts work, skip to the second part of this section.

Arenas: memory freed all at once

Bork does not free objects one by one. Every { ... } block owns an arena, a chunk of memory. Objects created in the block are carved out of that arena, and when the block ends the whole arena is released in one step. There is no per-object free.

arena of block { ... }
PairVec header"x" bytes

Ref<T>: a counted handle

A Ref<Node> points at an object that lives in some arena. The arena keeps two counters, strongCount and weakCount. A reference stored in an older arena than its target is strong (it keeps the target alive); one stored in a newer arena is weak (a back-edge). Whenever a Ref is stored, a counter goes up. So when the arena holding the reference dies, the counter must go down, or the target's arena would believe somebody still points at it. That is a leak.

Drop function. An arena can be told: "when you die, call this function on that object". Bork uses this to release the Refs inside an object. The runtime call is bork_arena_register_drop(arena, object, drop_fn).

What was already there

Before this PR, three places decided on their own whether a value needed a drop function:

Issue #62 asked for "glue generated from type capabilities, per generic instance". The concern: a generic container such as Pair<Ref<Node>, String> might leak its reference.

2. Intuition

The first idea is the obvious one: write a function that looks at a type, recursively finds every Ref inside it, and emits one big drop function. The compiler even has a query for that, TyCaps::needs_drop. But look at what actually happens when a class holds a Vec<Ref<Node>>:

arena A
Outer → field Vec header has its own drop → slot: Ref<Node>

The vector is an object in its own right. It was created by vec_alloc, which registered bork_vec_drop_refs on it at that moment. When arena A dies, that drop runs and releases the slot. Outer does not need to know. The same is true for a class inside a class and for an enum that holds a class: each piece registers itself when it is built.

So recursion would double-drop. If Outer also walked into the vector and released its slots, each reference would be released twice. The correct rule is local: register a drop for what you inline-own, and let every nested object register its own.

I checked this by running programs, not by reading code. The new test builds each shape in an inner block and checks that weakCount returns to its baseline afterwards. It does, for every shape.

Shape built in an inner blockweak count after block
Pair(r, "x")back to baseline
Outer(Holder(Vec<Ref>), r)back to baseline
Wrapped.Full(Holder(...))back to baseline
recursive Link<T> plus Pair(r, head)back to baseline

So the PR does the modest thing: it makes the existing decision visible and testable in one place, and pins the behaviour with a regression program.

3. The code

One module decides

enum_glue.rs is renamed glue.rs and gains two small functions:

pub(super) fn vec_drop_glue(&self, elem: TyId) -> Option<FunctionValue> {
    self.tcx.is_handle_clone(elem).then(|| self.vec_drop_refs_fn())
}

pub(super) fn enum_drop_glue(&self, name: &str) -> Option<FunctionValue> {
    self.enum_drops.get(name).copied()
}

None means "this type owns no inline Ref": no glue is emitted at all, which is the "no glue for Copy types" acceptance criterion.

Call sites ask the module

vec/alloc.rs used to test is_handle_clone(elem_ty) and look up the drop function itself; managed_ref.rs read enum_drops directly. Both now call the helpers above. The emitted IR is identical.

Tests

  • IR test: Copy-only enums, Pair<i32,i32> and Vec<i32> produce no bork.drop.* and no bork_arena_register_drop.
  • IR test: an enum with a Ref payload gets exactly one bork.drop.Slot; a Vec<Ref> uses bork_vec_drop_refs.
  • Program: programs/build/generics/glue_no_leak.bork with seven numbered checks (the exit code names the last failed one).
  • Goldens: five snapshot files gained lines for the new program; nothing was removed.

What is not here

TyCaps::needs_drop still has no codegen caller, clone glue is unchanged, and #63 (cross-region moves of generic structures) and #64 (negative tests) are untouched. Linking in my environment used a gcc stand-in for clang, so a run with the real one is worth doing.
