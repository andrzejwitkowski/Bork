1. Tło

Zanim przejdziemy do samej zmiany, przypomnijmy, na jakim gruncie ona stoi. Jeśli znasz już pipeline kompilatora Borka i jego model pamięci, przeskocz od razu do części „Co było przed tym PR”.

1a. Tło ogólne: potok kompilatora i areny

Dla początkujących: jak Bork zamienia tekst w program (kliknij, by zwinąć)

Kompilator Borka to potok kolejnych przekształceń. Każdy etap bierze reprezentację programu z poprzedniego i produkuje bardziej „skonkretyzowaną”:

Parsertekst → AST
→
TypeckAST → HIR z typami
→
Semawłasność, regiony, raport aren
→
Monogeneryki → konkretne funkcje
→
MIRbloki, skoki, wywołania
→
LLVMkod natywny

AST to drzewo składniowe — dokładnie to, co napisał programista. HIR to to samo drzewo, ale każde wyrażenie ma już typ. Mono (monomorfizacja) zamienia funkcje generyczne w konkretne kopie: id<T> użyte z i32 i z String staje się dwiema osobnymi funkcjami. MIR to prosty, płaski język pośredni: lokalne zmienne, bloki podstawowe, skoki i wywołania — łatwy do analizy i do przełożenia na LLVM.

Najbardziej nietypowa jest pamięć. Bork nie ma odśmiecacza ani ręcznego free. Zamiast tego każdy region (ciało funkcji, gałąź if, pętla) ma swoją arenę — kawałek pamięci zwalniany w całości, gdy region się kończy. Wartość „mieszka” w arenie, w której powstała. Problem pojawia się, gdy wartość ma przeżyć funkcję, która ją stworzyła: np. zwracany String. Wtedy wołająca funkcja przekazuje ukryty argument zwany result sink (zlew wyniku) — wskaźnik na własną arenę — i wołana alokuje wynik właśnie tam.

arena wywołującego (main)
imie = "bork"  ← wynik trafił tu przez result sink
arena wołanej funkcji (zwolniona po powrocie)
pomocnicza = "…"
Zapamiętaj Wartość, która ma przeżyć funkcję, musi leżeć w arenie wywołującego (przez result sink). Wszystko inne ginie razem z regionem. To jedyna rzecz, którą trzeba wynieść z tej sekcji — cała reszta PR jest odpowiedzią na pytanie „gdzie mieszka środowisko domknięcia?”.

Do tego dochodzi pojęcie widoku (view): wartość, która tylko pożycza coś z zewnątrz (&T), a nie jest właścicielem. Widok nie może przeżyć tego, co pożycza, więc Bork nie pozwala go zwrócić ani schować w polu czy zmiennej var.

1b. Co było przed tym PR

Przed zmianą domknięcie istniało tylko jako trailing closure — blok doklejony po wywołaniu:

fun apply(v: i32, f: (i32) -> i32): i32 { return f(v) }

fun main(): i32 {
    val k = 3
    return apply(2) { x -> x + k }   // trailing closure
}

Typeck sprawdzał ciało takiego bloku „w locie”, porównując je z typem funkcyjnym ostatniego parametru, a potem wyrzucał — w HIR zostawała tylko flaga has_trailing_closure: bool. Sema liczyła zmienne wolne na AST. A kiedy MIR dochodził do takiego wywołania, odpowiadał błędem Capability::Closure, a wywołanie przez wartość funkcyjną — Capability::IndirectCall. Skutek: żaden program z domknięciem nie kompilował się do pliku wykonywalnego, a funkcja generyczna nie mogła powiedzieć „daj mi coś wywoływalnego”.

Luka, którą ten PR zamyka Domknięcie nie było wartością: nie miało typu, nie dało się go zapisać w val, zwrócić z funkcji, ani ograniczyć w generyku (F: Fn(i32) -> i32). RFC 0006 §3.10 zostawiło to „późniejszemu RFC” — to jest ten RFC.

2. Intuicja

Całą zmianę da się streścić jednym zdaniem: domknięcie to funkcja plus środowisko. Funkcja to kod ciała; środowisko to zapamiętane wartości (albo adresy) zmiennych z zewnątrz, których ciało używa. Weźmy klasyczny przykład:

fun makeAdder(n: i32): (i32) -> i32 {
    return move (n) { x -> x + n }
}

val add3 = makeAdder(3)
val add8 = makeAdder(8)
println(add3(4))   // 7
println(add8(4))   // 12

Dwa wywołania makeAdder produkują domknięcia z tym samym kodem, ale innym środowiskiem. W czasie wykonania wartość domknięcia to po prostu jeden wskaźnik — na środowisko, którego pierwszym polem jest wskaźnik na kod:

arena main (przez result sink)
add3 → środowisko
kod = &makeAdder$closure0
n = 3
add8 → środowisko
kod = &makeAdder$closure0
n = 8
ramka makeAdder (już nie istnieje)
n = 3  martwe

Zwróć uwagę na to, co się tu dzieje z pamięcią. Gdyby środowisko leżało w arenie makeAdder, zginęłoby przy powrocie, a add3(4) czytałoby śmieci. Dlatego środowisko domknięcia move, które jest zwracane, jest alokowane w arenie wywołującego — dokładnie tak jak zwracany String.

Trzy rodzaje: Fn, FnMut, FnOnce

To, co domknięcie robi ze zmiennymi z zewnątrz, decyduje o jego rodzaju. Kompilator liczy go sam, skanując ciało:

RodzajCo robi ciałoPrzykładGdzie leży capture
Fntylko czyta{ x -> x + k }kopia w środowisku
FnMutprzypisuje do capture'a (albo woła na nim mutujące metody Vec){ -> n = n + 1 ; n }zwykłe: adres zmiennej zewn.; move: własna wartość w środowisku
FnOncewynosi capture'a (move x){ -> move s }— (jeszcze nie ma codegenu)

Rodzaje tworzą drabinkę: Fn ⊂ FnMut ⊂ FnOnce. Domknięcie Fn spełnia każde ograniczenie; domknięcie FnMut spełnia FnMut i FnOnce, ale nie Fn. Dlatego poniższy kod jest błędem typu, z komunikatem, który mówi, dlaczego:

fun apply<F: Fn() -> i32>(f: F): i32 { return f() }

var n = 1
apply({ -> n = 2 ; 0 })     // błąd: domknięcie jest FnMut (przypisuje do przechwyconej wartości)

Własność: zwykłe kontra move

Tu wchodzi model pamięci z części 1. Zwykłe domknięcie tylko pożycza to, co przechwytuje, więc jest widokiem — jak &T. Domknięcie move jest właścicielem swoich capture'ów, więc zachowuje się jak zwykła wartość.

zwykłe: { -> n }
środowisko (w bieżącym regionie)
kod
n → adres zmiennej n
nie wolno: return, var, pole, element tablicy
move: move (n) { -> n }
środowisko (w arenie przeznaczenia)
kod
n = 3  (własna kopia)
wolno: return, var, pole
Intuicja do zapamiętania Zwykłe domknięcie = „oto kod, a zmienne weź stamtąd, gdzie leżą”. Domknięcie move = „oto kod i własne dane”. Pierwsze nie może opuścić zakresu zmiennych, które pożycza; drugie może pójść wszędzie.

Sztuczka implementacyjna: lambda lifting

Zamiast uczyć MIR i LLVM nowego rodzaju „ciała domknięcia”, PR robi coś prostszego. Po monomorfizacji każde domknięcie jest wynoszone do zwykłej funkcji, której pierwsze parametry to jego capture'y:

// źródło
fun makeAdder(n: i32) { return move (n) { x -> x + n } }

// po wyniesieniu (mono)
fun makeAdder$closure0(n: i32, x: i32): i32 { return x + n }
fun makeAdder(n: i32)  { return MakeClosure(makeAdder$closure0, [n]) }

Dzięki temu MIR i kodgen widzą wyłącznie zwykłe funkcje; jedyna nowość to wartość MakeClosure (zbuduj środowisko) i wywołanie call_closure (załaduj kod ze środowiska i skocz). Ważny skutek uboczny: zachowany zostaje niezmiennik „jedna funkcja = jeden korzeń w raporcie aren”, na którym opiera się reszta kompilatora.

1

Parser: domknięcie jako wyrażenie

src/parser.lalrpop, src/ast.rs. Nowy wariant Expr::Closure i reguła ClosureExpr w Atom: { a, b -> ciało } oraz move (n) { a -> ciało }. Strzałka -> jest obowiązkowa — to ona odróżnia domknięcie od zwykłego bloku i pozwala uniknąć konfliktu w gramatyce LR(1) (domknięcie bez parametrów to { -> 1 }). Testy w tests/parser.rs pilnują też, że { x } i { val y = 1 } nadal są blokami.

2

HIR zachowuje ciało; nowy typ Closure

src/hir/mod.rs, src/ty/, src/infer/unify.rs. Call.has_trailing_closure zamieniło się w Call.trailing: Option<Box<HirExpr>>, a ciało trafia do nowego węzła HirExprKind::Closure { params, body, is_move, captures, kind }. W systemie typów pojawił się TyData::Closure { id, params, ret, captures } — każde wyrażenie domknięcia ma własny typ (przez id). Typy capture'ów siedzą w samym typie, więc podstawienie w generykach (T → i32) dociera do nich bez dodatkowej tablicy. Unifikacja traktuje Closure i Func o tej samej sygnaturze jako zgodne w obie strony; dzięki temu domknięcie można podać tam, gdzie oczekiwany jest zapisany w kodzie typ (i32) -> i32.

3

Cechy Fn, FnMut, FnOnce i rodzaj domknięcia

src/prelude/fn.bork, src/typeck/solve.rs, src/typeck/captures.rs (nowy, ok. 200 linii). Cechy są zwykłymi cechami prelude (trait Fn<A> {}) znajdowanymi po nazwie. Parser zamienia F: Fn(i32) -> i32 na Fn<(i32) -> i32> — jeden argument typu funkcyjnego, bo Bork nie ma krotek. Solver ma wbudowaną regułę: typ Closure albo Func implementuje cechę Fn* dla własnej sygnatury — o ile jego rodzaj na to pozwala. Rodzaj liczy captures.rs, skanując HIR ciała: odczyt → Fn, przypisanie lub mutujące Vec → FnMut, move x → FnOnce; zagnieżdżone domknięcie przenosi swój rodzaj na zewnętrzne. Parametr f: F z ograniczeniem jest wywoływalny (f(v)), a sygnaturę bierze z ograniczenia.

4

Własność: zwykłe domknięcie jest widokiem

src/ty/query.rs (stores_borrow, is_view_closure), src/typeck/env.rs, stmt/assign.rs, stmt/mod.rs. Zwykłe domknięcie z choć jednym capture'em „przechowuje pożyczkę”, więc działają dla niego istniejące reguły widoków: nie wolno go zwrócić, ani zapisać w var, polu, elemencie tablicy czy argumencie konstruktora (reject_stored_view_closure). Adnotacja typu zamienia Closure w zwykłe Func i gubiłaby tę informację, więc binding dostaje flagę view_closure, która towarzyszy nazwie przez val g = h i move h. Lista move (a, b) musi wymieniać dokładnie te zmienne, których używa ciało.

5

Mono: wyniesienie domknięć

src/mono/lift.rs (nowy). Po specjalizacji generyków przechodzi po każdej funkcji, zastępuje każde Closure węzłem MakeClosure { function, captures, kind, is_move } i dodaje funkcję outer$closureN(captures…, params…). Każda wyniesiona funkcja dostaje własny korzeń w raporcie aren (odczepiony od rodzica węzeł „Closure” z sema), więc niezmiennik 1:1 zostaje. Trailing closure staje się ostatnim argumentem wywołania. Funkcja ma pole env_params (ile początkowych parametrów to capture'y) i env_mode: ByValue (kopia, Fn), ByAddress (adres zmiennej, zwykłe FnMut) albo InPlace (własna wartość w środowisku, move FnMut).

6

MIR i LLVM

src/mir/body.rs, src/mir/build/expr.rs, src/codegen/llvm/lower.rs, declare.rs. W MIR są dwie nowości: Rvalue::Closure { function, captures, by_ref, arena } (zbuduj środowisko w danej arenie) i terminator CallClosure (wołanie przez wartość). W LLVM wartość domknięcia to pojedynczy wskaźnik na { wskaźnik kodu, capture'y… }. Domknięcie bez capture'ów to stała globalna, więc może przeżyć każdy region. Wyniesiona funkcja przyjmuje jeden wskaźnik środowiska zamiast capture'ów i ładuje je w prologu (albo, dla ByAddress/InPlace, używa adresu pola jako slotu zmiennej). Środowisko move domknięcia idzie do result sinku, gdy to ono jest zwracane, a w pozostałych przypadkach do bieżącej areny. Funkcje zwracające typ funkcyjny dostają ABI z result sinkiem.

Całość na jednym przykładzie: MIR dla makeAdder

Tak wygląda wynik bork build --emit-mir — to jest dokładnie to, co zamrażają goldeny w tests/golden/mir/closures.txt:

fn makeAdder (parent=true, sink=true) {
  let _1: i32 [Arg] n
  let _3: closure#0(i32)->i32 [Temp]
  bb0:
    _3 = closure makeAdder$closure0(copy _1) in result_sink   // środowisko w arenie wywołującego
    _0 = copy _3
    return
}
fn makeAdder$closure0 (parent=true, sink=false) {
  let _1: i32 [Arg] n          // capture, ładowany ze środowiska
  let _2: i32 [Arg] x
  bb0:
    _4 = add(copy _2, copy _1)
    _0 = copy _4
    return
}
